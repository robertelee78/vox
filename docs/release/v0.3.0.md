# Release v0.3.0: features, built on v0.2.10

- **Status**: accepted. The decider's release policy, 2026-09-26: v0.2.10 is every known defect in what Vox ships; v0.3.0 is features, built on v0.2.10; v0.3.1 is the new features' defects. On 2026-09-28 the decider approved this plan's board: "v0.3.0 gets its own board, like v0.2.10". The decider, 2026-10-01: "vox is a super important tool in my dev work on other projects… I need v0.3.1 to become usable asap". So v0.3.0's work runs in parallel with v0.2.10's finish, on `integrate/v0.3.0`.
- **Scope**: the features built for PRD-001 on `prd1/v030` (PRD-001's work, Project 20, root #176), carried onto v0.2.10, with every claim they make measured through the shipped binary. The feature list below is as built on `prd1/v030`; the decider confirmed it as the scope on 2026-10-01 (see Decisions).
- **Built on v0.2.10**: v0.3.0 carries every v0.2.10 commit. The merge onto v0.2.10 is `merge/v030-on-v0210`, by vox-0e. When `integrate/v0.2.10` moves on, its new commits are merged in too.
- **Defects in the new features**: a defect found in a v0.3.0 feature before v0.3.0 ships is fixed in v0.3.0 when it blocks the feature's own claim (the items in B and C below). Every other defect in the new features belongs to v0.3.1. A defect in what v0.2.10 ships belongs to v0.2.10, and its fix is ported off the feature branch.
- **Integration owner**: the `vox` session. Each item lands with a real-binary before/after measurement and a mutation check, and an independent verifier accepts it. One integrated release gate runs at the end.
- **Delivery boundary**: an item is delivered when it is included in the published vox v0.3.0 GitHub release.
- **Evidence rule**: as v0.2.10's, under the test rules in `AGENTS.md` (ADR-018, "What may block a release, what is optional, what is deleted"). A test exists only if it is user-facing: it drives the shipped `vox` as a person would and asserts what that person sees or gets. Every red names product or test. A proof is run once, and repeated only on smoke (a red, a flake someone has seen, a timing near its bound, or a claim that is itself a rate). Optional proofs never block, neither CI nor the release gate. Every participant in a proof runs as the shipped `vox` (ADR-018, "Only real use of the product is a test"). A proof must force the condition it measures and print its count even when it passes. A red is classified as the product broken, the proof asserting a withdrawn model, or the proof unable to measure; it is never put down to load.

This is the planning source for the v0.3.0 work items. Each item has a stable ID, and issues quote it. The features themselves keep their requirements in PRD-001 and their milestones in ADR-022 and ADR-023 (on `prd1/v030`); this document does not restate them.

## A. The features `prd1/v030` carries

As built on `prd1/v030` (`c64c3e3`, from `git log origin/main..origin/prd1/v030`); confirmed by the decider as v0.3.0's scope on 2026-10-01. One line each, named by PRD-001 requirement or ADR milestone.

- **ADR-022 M22.1, M22.2 / PRD-001 R27**: the datagram seam; relayed traffic loses packets instead of stalling behind them (`9b2ec02`).
- **ADR-022 M22.3, M22.4 / PRD-001 R25**: UDP services cross Vox: `vox serve 53/udp`, `vox forward <name>.vox 53/udp`, SOCKS5 UDP ASSOCIATE (`c0cc0b9`).
- **ADR-022 M22.5 / PRD-001 R29**: the app API: a program on one member node opens a live stream and datagram flow to a program on another (`e4e2ff9`, `377718a`).
- **ADR-023 M23.2 / PRD-001 R13**: every node shows a room's messages in one order, and a reply follows what it answered; a clock a day ahead cannot drag the order (`c065a37`, `3f91109`, `73ca24f`).
- **ADR-023 M23.3 / PRD-001 R11**: a member who is never online with the sender still gets its key, through any member who is; key-packages are sealed one-shot (`0e2d269`, `2279141`).
- **ADR-023 M23.6 / PRD-001 R6–R10**: retention: a room's admin sets disappearing messages, a node keeps less, the shorter wins, and an expired message leaves nothing visible (`24b4433`, `c50b277`, `b78a6d9`, `e2a74b9`).
- **PRD-001 R12, R14**: an approver chooses whether a newcomer reads their history, and superseded keys are deleted (`907c4b2`).
- **PRD-001 R18**: `vox share` serves a file or folder to a room over HTTP, and `vox room get` lands it safely (`abf9339`, `7016d3b`).
- **PRD-001 R20 / ADR-017 decision 12**: local names: `ssh nas.family.vox` reaches the node you named nas, in the room you call family (`3622bd4`).
- **PRD-001 R28 / ADR-013**: the family LAN: a room becomes a LAN for its trusted members, and only listed ports are reachable (`8cefbee`, `f8ca4b4`).
- **PRD-001 R30, R31**: an app embeds the Vox node: VoxFFI.xcframework for iOS and macOS, driven from Swift (`1e02ed4`).
- **PRD-001 R35, R38**: `vox status` shows what the node is doing and flags what is wrong; the daemon serves metrics (`4259782`, `bab1a22`).
- **PRD-001 R37**: a daemon notifies its operator once when something goes wrong and once when it clears (`4c5b506`).
- **PRD-001 R36**: common failures say what went wrong and what to do (`06ba231`, `6e38b3c`, `601580e`).
- **PRD-001 R19**: an agent's drain says whose words the room's are, cannot be forged by another author, and a backlog does not flood a turn (`2b124f0`, `e7d6bae`, `f222f1a`).
- **PRD-001 R43**: deniable rooms are removed; every existing room keeps its name (`b0f8218`).

## B. Carrying v0.2.10 and measuring every claim

### V030-01 — v0.3.0 carries v0.2.10, with the control protocol reconciled (#226)
**Why.** Found by vox-0e on 2026-09-27 from a trial merge of `integrate/v0.2.10` `1de7548` into `prd1/v030` `c64c3e3`: 22 files and 66 hunks conflict. Most are unions. The control protocol diverged on both sides: v0.3.0 added `Order`, `SetRetention` and `Rename` requests, 6-field rows and page marks; v0.2.10 added `Rooms` paging, `MalformedIpc`, and new wire codes, among them `0x0C NotYetMember` and IPC tag 2081 `RoomNotRemembered`. The merge is `merge/v030-on-v0210` (at `5ca9736` on 2026-09-28), where the full gate found five defects that neither side has alone, each fixed with its red before and green after.
**Acceptance.** `prd1/v030` carries every v0.2.10 commit, merged on purpose where the two sides changed the same thing, with the protocol's request, frame and event tags and version reconciled. The workspace builds. Every proof on both sides is green, or is a tracked item. Commits that land on `integrate/v0.2.10` after `1de7548` are merged in too.
**Validation.** The full macOS gate on the merged tree, plus CI's Linux run.

### V030-02 — v0.3.0's proofs run every participant as the shipped `vox` (#227)
**Why.** Found by vox-0e on 2026-09-27. Eleven of v0.3.0's proofs spawn a node or endpoint in-process (`Node::spawn_networked`, `Node::spawn_config` or `VoxEndpoint::bind`), even where their headers say "proved with the shipped binary", so their claims are unmeasured. The claims: ADR-022 M22.5 (app API), PRD-001 R18 (share), R37 (notify), R20 (local names), R30/R31 (FFI), R28 (family LAN), R6/R7/R10 (retention), R13 / M23.2 (one order), R35/R38 (status and metrics), M22.1 (datagram seam) and M22.2 / R27 (relay loses packets). The last three needed the deleted `vnet.rs` and are deleted in the merge.
**Acceptance.** Every claim above is accepted on a proof in which every participant runs as the shipped `vox`, with its own mutation. No v0.3.0 proof runs a node or endpoint in-process, except a deliberate attacker that is not a product participant, as RP-04 did. Where a conversion had to weaken a claim, that is V030-07's.
**Validation.** Each converted proof's own, plus a grep of v0.3.0's tests for `Node::spawn*`, `NodeConfig` and `VoxEndpoint::bind` that finds only attacker endpoints.

### V030-03 — The two formerly excluded `causal_order_proof` tests are fixed, not excluded (#228)
**Why.** `prd1/v030`'s `ci.yml` excluded two tests from the blocking gate by name and ran them only in a report-only `flaky-watch` job: `three_members_one_offline_for_a_while_show_one_order` ("second joiner cut off (v0.2.9), ADR-023 M23.2") and `a_late_arrival_after_a_restart_is_marked` ("V29-23 (#104)"). v0.2.10 removed exclusion by name and `flaky-watch` (V210-19, #192), so after the merge both are in the blocking gate.
**Acceptance.** Each test's red is caused, named and fixed. Each passes in repeated runs on both OSes and goes red under a mutation that restores its cause. `ci.yml` names neither of them.
**Validation.** Repeated runs of `causal_order_proof` under the timing lock, and CI on Linux.

## C. Product gaps found while converting the proofs (#227)

vox-0e found these on `merge/v030-on-v0210` while converting the family-LAN and local-names proofs to real `vox` processes (`6daa7d1`, `a7ce70f`). Each is a gap in a v0.3.0 feature that a person meets, and each forced a proof to work around it.

### V030-04 — `vox lan up` serves a control socket and metrics
**Why.** A running `vox lan up` holds its profile but serves no control socket and no metrics. So `vox status`, `vox trust remove` and every `vox room …` verb cannot reach it, and it reports no app-layer counters. The family-LAN proof (`6daa7d1`) could not read alice's refusals of carol for claim 2, and had to stop alice's LAN to withdraw trust for claim 8.
**Acceptance.** A running `vox lan up` serves the profile's control socket as `vox daemon` does: `vox status` (with its app-layer counters) and the metrics endpoint answer, and `vox trust add/remove` and the `vox room …` verbs act on the running node. Withdrawing trust from a running LAN ends the link without a restart (R22).
**Validation.** The family-LAN proof asserts claim 2 on alice's counted refusals of carol, read from `vox status --json`, and claim 8 with `vox trust remove` against the running LAN. A mutation that stops `vox lan up` serving the socket goes red.

### V030-05 — The profile-busy message is true while `vox lan up` holds the profile
**Why.** A verb run while `vox lan up` holds the profile is told "a vox is already running for this profile … Its control socket is …", and to "use the `vox room …` verbs, which ask the running node". Nothing listens on that socket, and the `vox room` verbs cannot reach a `vox lan up` (V030-04). The remedy it gives does not work.
**Acceptance.** Whatever holds a profile, the message a person gets names what holds it and a remedy that works. If V030-04 makes `vox lan up` serve the socket, the existing message becomes true, and that is shown.
**Validation.** A real-binary proof runs `vox trust remove` (and one `vox room` verb) while `vox lan up` holds the profile, and asserts the message and that its remedy succeeds when followed. A mutation that restores the old message for this holder goes red.

### V030-06 — A service can be added to a running daemon
**Why.** `vox service add` opens the profile itself, so it cannot run beside the daemon that holds it. The local-names proof (`a7ce70f`) has bob and carol stop their daemons, add the service, and start again on the same port with their room passphrases, as a person would have to. (`vox service remove` already asks the running node.)
**Acceptance.** `vox service add` against a profile whose daemon is running asks that daemon, and the service is offered without a restart. Without a running daemon it keeps working as now.
**Validation.** The local-names proof offers bob's and carol's services with their daemons running. A real-binary proof shows a service added to a running daemon is reachable by a trusted member without a restart, and a mutation that routes the verb back to opening the profile goes red.

### V030-07 — Proof claims weakened by the conversion are accepted by the decider or restored by product work
**Why.** Converting to real `vox` processes (#227) weakened three claims:
- **family LAN, claims 2 and 8** (`6daa7d1`): claim 2 asserts carol's links, watched for longer than her longest redial, instead of alice's counted refusals; claim 8 stops alice's LAN to remove trust instead of withdrawing it from a running LAN. Both follow from V030-04.
- **local names, join order** (`a7ce70f`): carol now joins `family` before alice does, so alice learns carol when she joins, not afterwards from the board. The proof's precondition ("carol joined through bob, so alice learns her as a member from the board, not from a join of her own") no longer holds; a later member learned through the board is no longer exercised.
- **app API, case 6** (`a80198f`): "200 stalled app streams cannot starve the room" has no mutation; the conversion's commit names mutations for no case.
**Acceptance (decider, 2026-10-01: "restore if they're valid tests. I just hate foot guns").** Each weakened claim is restored by a proof that drives the shipped `vox`, asserts what the person sees, and whose every red names product or apparatus. A claim whose test cannot be made to tell a broken product from a broken test is deleted, not kept weak. The LAN claims are restored once V030-04 lands. The local-names proof is changed so a later member really is learned from the board. App API case 6 goes red under a mutation that lets stalled app streams starve the room.
**Validation.** Each proof's header and assertions, read against its claim; each restored claim red under its mutation. App API case 6's mutation run, with its count printed.

### V030-08 — A node can leave, forget and end rooms cleanly
**Why.** The decider (2026-09-28): agent rooms are ephemeral, and even long-lived rooms (friends, coworkers, family) number at most a couple hundred per node. So leaving a room has to be clean. Today the only exit is the TUI's `:close`. It has no CLI verb, so an agent cannot use it. It keeps the room's data on disk, and the other members still count the node as a member and keep trying to deliver to it. Nobody can end a room for everyone.
**Scope (decider, 2026-10-01): leave, forget, and end; plus an optional idle end the creator chooses.**
- `leave` (CLI and TUI): the node leaves the room's swarm. It is no longer a member, and the others stop syncing with it. No key rotation on leave ("the node that left is no longer in the swarm/room").
- Rejoin: the same identity can rejoin later the ordinary way, with the room's name and passphrase (there is no invite model). The leaver's signed feed restarts safely.
- `forget`: delete the room's data from this node. On a room still joined, it leaves first.
- `end`: the room's creator, or an admin the creator delegated, closes the room for everyone. No new messages are accepted; history stays on each node until that person runs `forget`.
- Idle end: NOT a fixed lifetime. The creator may choose, at `vox room create`, that the room ends after a set IDLE time (measured from the last signed activity). Off unless chosen.
**Acceptance.** Each verb works through the shipped CLI (so an agent can use it) and the TUI. After `leave`, the other members stop syncing and delivering to that node within a bound. After `forget`, none of the room's data remains on the node. After `end`, every member sees the room as ended and no new message is accepted. A creator-chosen idle end ends the room only after the chosen idle time with no activity, and never when the creator didn't choose it.
**Validation.** Real-binary proofs per verb, each with a mutation that goes red.

### V030-09 — Room creation does not slow down as rooms accumulate (deferred from v0.2.10)
**Why.** Found by adr-020 while measuring #189 at 1,600 rooms. Each hundred creates took 6.8 s at first and 34.6 s by 1,500. That is roughly linear growth per create, and its cause is not identified (the open-rooms set re-seal alone does not explain ~300 ms per create). The decider deferred it on 2026-09-28: it is invisible at the realistic couple hundred rooms per node.
**Acceptance.** Creating a room costs about the same at 200 rooms as at 1, or the cause is shown to be bounded well below a person's notice at the decider's scale.
**Validation.** A timing proof across a couple hundred creates, with the cause named.

### V030-10 — A pruned message never makes its author unreadable (from v0.2.10 #265)
**Why.** v0.2.10's #265 (V210-74) sets aside a log entry that arrives without its payload ("Withheld"), because in v0.2.10 only a hostile peer strips payloads. v0.3.0 prunes payloads legitimately: an expired message keeps its signed skeleton (ADR-023). Merged as is, a member who joins late or lags behind would receive honest pruned skeletons, set them aside, and stop reading that author for good. Found by #265's verifier; raised by adr-020 on 2026-09-29.
**Ruling (the decider, 2026-10-01).** "when we have an envelope that indicates that I should expect a body, if I have not received it yet, I know to keep asking for it. Removes the ability for the bad actor to strip a message effectively." This replaces v0.2.10's set-aside rule for v0.3.0: a peer can delay a body, if it is the receiver's only source, but cannot make it disappear.
**Acceptance.**
- A signed skeleton is always accepted, so the author's feed never stops, whether or not its body came with it.
- A body is "expired" only when the receiver itself computes, from the entry's signed `claimed_ms` and the room's signed retention (or the receiver's own shorter retention), that the entry is past retention. Nothing a peer says or omits makes a body expired.
- Otherwise the body is owed: it is shown as "not received yet", and asked of every peer until one supplies it. Once supplied, it is shown.
- A late joiner reads every author after one of their messages expires.
**Validation.** Real-binary proofs, each run once, with a mutant that goes red:
- A late joiner after an expiry reads the author's later messages, and the expired one shows as expired. Mutant: v0.2.10's Withheld rule unchanged (the skeleton is set aside).
- A peer strips an in-retention body. The receiver shows "not received yet", and gets the body from another peer that holds it. Mutant: a skeleton without a body is treated as expired.
- The stripping peer is the only source. The message stays "not received yet", never "expired", and the feed carries on past it. Mutant: expiry taken from the peer rather than computed by the receiver.

### V030-11 — Tunnels can be found and closed (the decider, 2026-10-01)
**Why.** The decider's ruling of 2026-10-01: a person must be able to see their live tunnels and close one without untrusting anyone or removing a service, and a tunnel that is stuck must not hold its resources for ever. v0.2.10's #272 is to bound tunnels per member (past the cap of 16, a new tunnel is refused with a reason that says how to free one) and to list live tunnels in `vox status` (member, service, opened, last moved). This item builds on both, and starts on `integrate/v0.3.0` once #272 lands.
**Acceptance.**
- **A close verb.** On the host, a person closes one member's tunnels to a service, or all of that member's tunnels (for example `vox tunnel close <member> [service]`). On a guest, a person closes one SOCKS or forward session. Neither untrusts anyone or removes a service, and the closed tunnel's far end is told it was closed.
- **The TUI shows live tunnels**, and a person can easily select one and close it, if they want to.
- **A stuck tunnel is closed on its own.** A tunnel is stuck when data is waiting to be sent and the far end has read nothing for a long time (10 minutes by default). It is closed, and the reason is said where the person looks (`vox status`, the TUI). **An idle tunnel with nothing pending is never closed**: an idle ssh session survives (RP-09).
**Validation.** Real-binary proofs, each run once, with a mutant that goes red: a closed tunnel stops carrying and its far end ends, while the member stays trusted and the service stays served; the TUI lists the tunnel and closes the one selected; a tunnel whose far end stops reading with data pending is closed after the configured time, and an idle ssh session past that time is still open.

### V030-12 — A stranger's held relayed joins never keep a relayed joiner from another host off the board (found carrying #286)
**Why.** Found by carry-v030 on 2026-10-01 while carrying v0.2.10's #286 (V210-92). Its proof `a_relayed_flood_from_one_host_does_not_keep_a_relayed_joiner_from_another_out` passes on v0.2.10 `5a2c1c23`: the anchor carries 17 circuits, and carol's join gets in in 8.1 s. On the carry onto v0.3.0, it went red in 2 of 2 runs. Carol's join ends "the anchor could not be reached, so no member was asked … steps: board (unreached) 30.51s", she asks for no circuit, and the anchor carries at most 16. Without the stranger's 16 held joins, the same carol joins the same kind of room through the same anchor. So while a stranger holds relayed joins open, something on v0.3.0's path to the board is used up, until the cause is shown to be the carry's own conflict resolution instead.
**Acceptance.** While a stranger holds every join slot of a member through relayed joins from one host, a joiner from another host reaches the board, is relayed, and gets in, on v0.3.0 as on v0.2.10. The cause is named.
**Validation.** #286's relayed-flood proof, run once on `integrate/v0.3.0` with the v0.2.10 carry, passes; a mutant that restores the cause goes red on its assertion.

### V030-13 — A room's creator can make and unmake admins (the decider, 2026-10-01)
**Why.** V030-08 lets the creator or an admin the creator delegated end a room, but the shipped `vox` has no command to delegate an admin (`vox grant` was removed in M17). The decider ruled on #244 (2026-10-01) to add one in v0.3.0.
**Acceptance.** `vox room admin add|remove <member>` is run by the room's creator only, and is refused for anyone else with a reason. An admin added this way can end the room, and a removed admin cannot.
**Validation.** Extend the V030-08 proof with an arm where the creator adds an admin and that admin ends the room, and an arm where a non-creator's `admin add` is refused. One mutant per claim.

### V030-14 — Leaving or ending a room withdraws its records from anchors (the decider, 2026-10-01)
**Why.** The board protocol can only put and get, so anchors keep a left or ended room's records until they lapse: the address for 2 h, the bundle for 7 days, and the genesis indefinitely. The decider ruled on #244 (2026-10-01) that leave and end must leave no stale anchor records.
**Acceptance.** A signed withdraw, accepted only from the record's author, removes a leaver's address and bundle records at `vox room leave`, and the room's records at `vox room end`, from every anchor holding them. An unsigned or forged withdraw is refused.
**Validation.** A real-binary proof reads the anchor's board after leave and after end and finds no stale records. An attacker's forged withdraw is refused (attacker as apparatus). One mutant per claim.

## D. Agent comms, from the agent-tincan review (the decider, 2026-10-01)

adr-020_adr-021 ran a read-only study of `/opt/agent-tincan` (HEAD `dce1e28`), a relay-based agent messaging tool, and the decider ruled on what Vox takes from it in a product interview on 2026-10-01. The governing principle is in Decisions below: **Vox never spawns instances of anything**; it is a transport layer with apps on top. Every item here uses only sessions a person opened and nodes already in the room. The defects the study found in what v0.2.10 ships are v0.2.10 items: V210-121 (#322) and V210-123. ADR-020 is amended to match (§6, §9).

### V030-15 — A wake announces; the message itself arrives once, through the room read
**Why.** Today an urgent wake puts the sender's whole message into the harness's user-role message, the slot where the operator speaks, and the per-turn read then shows it again. v0.2.10's #308 (V210-112) stops the second copy by matching the wake's text in the prompt. Tincan's wakes carry only a count and the senders, never content (`internal/wake/wake.go:26-27`), and recount before they fire (`:459-472`). Measured on Claude Code 2.1.287 (2026-10-01): a message written to its messaging socket runs `UserPromptSubmit` with that message as `prompt`, whether the session is idle, mid-generation or between tool calls. So the drain delivers the body in the very turn the wake starts.
**Acceptance.**
- An urgent wake carries only "N urgent messages addressed to you from <petnames> in room <name>", plus what to do if the room read shows nothing new. No byte of any message body or other author-chosen text reaches the harness's user-role message.
- The drain delivers each woken message exactly once, in the same turn, showing urgent addressed rows (and V030-20's replies) first within its 50-message / 16 KiB bound.
- The daemon recounts unread urgent addressed rows past the session's cursor just before it wakes, and sends nothing when there are none.
- A session has at most one wake outstanding: no further wake until its cursor moves or 10 minutes pass. This dedupes; it drops nothing.
- #308's prompt matching and woken set are removed.
- Codex is unchanged: it has no wake path.
**Validation.** Extend `an_agent_wake_is_safe_and_bounded_proof` and `remote_interrupt_proof`. An urgent message carries a unique canary:
- no byte of it reaches the wake endpoint;
- in the live Claude and OpenCode cases the model is given it exactly once;
- when the drain runs before the wake fires, the daemon sends nothing.

One mutant per claim (the body back in the wake; no recount; no outstanding-wake rule). Every red names PRODUCT or APPARATUS.

### V030-16 — `vox agent doctor` says whether a session is wired up, and `vox room ping` checks it from the other side
**Why.** A hand-opened session needs a hook or plugin installed once, and when it isn't wired up nothing says so. F17 (OpenCode registering as `unknown`) went unseen this way. Tincan's `doctor` (`internal/cli/doctor.go:90-192`) prints one fix line per fault, and tells "the app never started it" from "it started but was never used" by records the server writes itself (`internal/mcpserver/launchlog.go`). Its fix commits warn that a wrong verdict sends the agent the wrong way (`d950fb3`). Its `ping` is answered by the plumbing, never the model (`internal/client/ping.go:22-88`).
**Acceptance.**
- `vox agent doctor [--json]` reports ok, warn or fail with a one-line fix for each of:
  - the node is running and answers;
  - the room resolves;
  - the Claude Code hook entries (`UserPromptSubmit` and V030-20's `Stop`) exist once, at user scope;
  - Codex's hook is trusted;
  - the OpenCode plugin file is the current build;
  - a drain self-test passes;
  - each session's record: first seen, last drained, idle or busy, wake endpoint alive;
  - trust in each direction per member;
  - the members' version stamps.

  It exits non-zero on any fail.
- `vox room ping <name>` posts a ping that the target's **daemon** answers, never its model, saying which sessions answer to that name, whether each is reachable, and when it last read. Pings and pongs never reach a model and never wake anyone. A missing answer is reported with what it does not prove: offline, not trusting the sender, or no session. The decider accepts that a pong shows trusted room members which sessions a node has.
**Validation.** For each check, a real-binary case that breaks exactly that one thing asserts its fix line; a case whose breakage did not happen is APPARATUS. One mutant inverts a check. A ping round trip between two profiles, a ping to a stopped node (a named timeout), and no ping or pong in any drain.

### V030-17 — A sender is told how each addressee can be reached
**Why.** An urgent message to a session that cannot be interrupted (Codex) says nothing to its sender today. The daemon's "cannot interrupt" note goes only to the target node's stderr. Tincan's send result says when to expect a reply (`internal/client/render.go:58-75`).
**Acceptance.**
- A session's `hello` says how it can be reached (`data.wake`: `interrupt` or `turn`).
- `vox room post --to` reports, per name, what to expect:
  - "codex: urgent will not interrupt it; it reads at its next turn";
  - "no session has announced itself under this name";
  - "last posted 3h ago";
  - and either direction of trust.

  It never claims "overdue", since Vox cannot see another node's reads.
**Validation.** Two profiles: a Codex-shaped session is reported as "will not interrupt", and an unknown name as unannounced. One mutant drops `data.wake`.

### V030-18 — The per-turn room read spends its tokens on what is addressed to the agent
**Why.** The drain injects every unread row in full each turn, including coordination chatter (`hello`, `status`, claims). This lands in the model's context every turn.
**Acceptance.** Rows addressed to the session go in full. Other agent coordination traffic goes in as one line with a count, and `vox room read` has the rest. Unaddressed prose stays in full. Attribution, continuation prefixes and the cursor rule are unchanged.
**Validation.** A real-binary drain with addressed rows, chatter and prose asserts each is rendered as stated, and the injected size. One mutant renders chatter in full.

### V030-19 — A reply shows what it answers
**Why.** A drained reply shows only `[entry from author]`. An agent that forgot the question loses the thread. Tincan's commit `618f49d` was a woken agent that read a reply and never finished the task waiting on it.
**Acceptance.** A row whose `re` names an earlier message shows a one-line preview of that message: its entry, its author, and its first words, rendered and capped like any row.
**Validation.** A real-binary drain shows the preview, and an author cannot forge a different preview. One mutant drops it.

### V030-20 — An idle agent is told when a reply to it is waiting
**Why.** Only urgent addressed messages wake a session (ADR-020 §6). An agent that asked something and went idle has no next turn, so the answer can sit unread indefinitely. Tincan nudges an asker whose reply sits unseen (`internal/wake/wake.go:178-186, 321-344, 466-526`). The decider ruled that Vox does so too (2026-10-01), changing ADR-020's urgent-only rule for this case.
**Acceptance.**
- **What counts:** a reply is a row whose `re` names a post by this session that addressed someone. It is not the session's own, and not `ack`, `status`, `hello`, `bye`, `ping` or `pong`.
- **When it is sent:** while such a reply is unread (the session's cursor has not passed it) and the session is idle, the session gets an announce-only notice (as V030-15), and again 5, 20 and 60 minutes after each previous one, then no more. A fresh reply restarts the series. A busy session is told at its next end of turn.
- **When it stops:** the reply is read, the series ends, or the session is gone.
- **Idle and busy come from the harness:** Claude Code's `Stop` and `SessionEnd` hooks run `vox agent hook`, which records idle or ends the registration and prints nothing; `UserPromptSubmit` records busy. A session busy for over 10 minutes with no hook activity counts as idle. `vox agent plugin claude` prints the new entries, and V030-16's doctor checks them. OpenCode's idle event and Stop on an interrupted Claude turn are measured before building.
- **Survives restarts:** the series state lives in the session record, so a daemon restart resumes it. It is never a cap: the reply is always delivered at the session's next turn.
**Validation.** Two profiles, with a reply carrying a canary:
- idle → exactly one notice, carrying no canary byte;
- busy → none until Stop;
- read first → none;
- a fresh reply restarts the series;
- a daemon restart resumes it;
- live Claude (opt-in) → the canary is given once.

One mutant per claim. The 5/20/60-minute steps are opt-in unless the schedule is a real setting the proof can shorten.

### V030-21 — Room text can never close its own fence on OpenCode, nor be labelled the user's
**Why.** The OpenCode plugin wraps room text in a fixed `<vox-room …>` … `</vox-room>\n\nThe user's message:\n` block. Nothing escapes the tag, so a message containing `</vox-room>` can appear to end the block. And when a relayed wake's turn also drains other messages, the wake text follows "The user's message:". Tincan's council fences each stage with a random nonce drawn after the fenced text exists (`internal/council/engine.go:215, 291`; `chairman.go:70`). The decider placed this with the wake rework in v0.3.0.
**Acceptance.** The plugin's fence tag carries a random nonce drawn each turn after the drain returns, and only that tag ends the block. `<vox-room`/`</vox-room` inside room text are defanged. A relayed wake is labelled as relayed by Vox, never as the user's message.
**Validation.** The live OpenCode proof (`opencode_plugin_proof`) posts a message carrying `</vox-room>` and a fake "The user's message:" line. What the model was given shows it inside the fence, and the wake text never follows "The user's message:". One mutant per claim.

## Upgrading to v0.3.0

**Rooms made before v0.3.0 do not open in v0.3.0** (decided by the decider on 2026-09-29).
- **Why:** a room's messages now carry what their author had seen, so every node shows one order (ADR-023). v0.3.0 does not read the older format.
- **What you see:** after updating, each existing room says "this room was made by vox before v0.3.0 … make the room again".
- **What to do:** create the room again with `vox room create`, and invite its members.
- **What is not touched:** nothing is converted and nothing is deleted; the old room simply does not open.
