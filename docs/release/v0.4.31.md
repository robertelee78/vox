## How to read a task

Each task is one work unit with five fields, written so an agent can build it without reading the source sections:

- **Why**: the problem a person hits on v0.4.30, with the fix-list item numbers (and an experiment's verdict line only where it is the evidence). An item maps to exactly one task in Coverage A; another task's Why may mention it as context.
- **What**: the proposed solution as the person will see it.
- **How**: the design, as short bullets pointing at the frozen ADR decision ids (and code locations at the tag where known). The ADR is the authority; the bullets never restate it.
- **Acceptance criteria**: observable, checkable outcomes. Always (a) the proof journey and the existing file it extends; (b) the red on v0.4.30 and what the person sees there; (c) the green on the candidate; (d) the mutant that turns it red. Then every finding owed to the task (row 83), restated in plain words with its source tag, e.g. `(re-check 3 R12-F4)`, `(task cut, V431-040-06)`. Every proof drives the shipped `vox` as a person would, names PRODUCT or APPARATUS on every red, adds no unit test, and deletes the tests it makes redundant (AGENTS.md); a fleet journey is built by the first task whose act it carries. "Owed: this run" or "re-run" means the task takes the v0.4.30 red itself, the old receipt having been lost in the reboot of 2026-11-13.
- **Depends on**: build-list ids only, for what the task needs before its own acceptance can be met. No dependency points forward; where an act needs a later task's surface, it is "qualified in" that later task, and both say so.
- **Replaces**: the `V431-0NN-MM` source task ids, where there are any.
