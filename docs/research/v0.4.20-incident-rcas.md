## 1. Failed join and board rollback

### Failed join and local-board rollback — full RCA and corrective plan

**Status: diagnosis and proposed design only. No implementation, approved compensation mechanism, candidate, acceptance or publication is claimed.** This concerns all failed join stages and rejection of an existing room's live publication, not only a duplicate name. It does not authorize a change to computer trust, cryptographic admission, real room-end protections, retained history, or another defect's repair.

#### Exact failure mechanism

1. `actor.rs:3659–3697` prepares a signed **Member** board withdrawal before pre-join publication, and can refresh it at the proposal's exact epoch/time. In `joinstream.rs:1008–1059`, mutual PAKE proof succeeds, the responder's proposal is verified, `prepare_before_admission` durably retains rollback, **then** the joiner sends `AdmissionPrepared`. `run_responder` (`joinstream.rs:1237–1291`) verifies the matching proposal hash, commits admission through its callback, then sends `Accepted` with name. Proposal's separately signed five fields are room, epoch, joiner, responder, timestamp (`joinstream.rs:112–160`); it currently contains no name. Accepted's name is not covered by that signature. Do not describe existing preparation as happening after acknowledgement or treat that name as signed.
2. Only after `Accepted` does local construction compare the proposed display name with the published `room_named` view (`construction_save.rs:244–261`); collision invokes `begin_metadata_abort_join`. ADR-028 R-3 deliberately permits one held room per name because names participate in service addresses; same-name/different-ID joins remain refused unless that ADR is explicitly amended. Existing same-ID short-circuit is different. Local refusal after responder admission creates a half-join: a Member board withdrawal is not a governance departure, so the responder's roster may still include the guest.
3. `queue_abort_join` / `queue_join_rollback` (`metadata_save.rs:3956–4012`) promote retained cleanup to pending withdrawal and purge partial local state. `install_metadata_journal:2197–2221` maps **any** `delta.purged` to `retract_live_channel`; `actor.rs:18752–18774` clears live work, membership and calls `net.forget_room_on_board`; `network.rs:2651–2656` calls `withdraw_room(cid, None)`. `nat/store.rs:410–458` removes discovery/cache state and inserts a `withdrawn_rooms` key even without signed end. `store.rs:625–631, 945–955` then refuses every author's records and genesis for that room. A later successful join removes its completed cleanup journal but does not undo that key. The Member withdrawal sent to peers cannot explain rejection of another author's records; the whole-room local marker can.
4. This is not limited to the late name check. `Joiner::retain_board_cleanup` exists before announcing prejoin, so a wrong passphrase or other failure before a proposal can still require cleanup; `JoinerLost` is handled through abort (`actor.rs:10638–10676`). A true failed pre-publication route can be removed by the existing answered-refusal path, but do not assume all failure paths reached or avoided that state. Failures after preparation, after remote admission, during sealing/construction, policy, publication, cancellation or crash need distinct treatment based on owned state and actual commit uncertainty.
5. `reject_existing_live_channel` (`actor.rs:18745–18749`) also calls the same retraction for an existing stored room when its open/publication is rejected, including a computer-policy lifetime rejection (`metadata_save.rs:1625–1667, 1744–1771`). Although it intentionally retains stored room rows and should allow a later authorized reopen, it poisons the same board. This is source-established; no separate runtime reproduction is claimed.

The board can reject unpinned remote genesis at the service policy gate before store withdrawal (`nat/service.rs:1516–1537`), so a policy diagnostic does not refute the terminal-marker chain. Existing retained logs and tests do not establish restart as recovery or repair.

#### Classify every purge producer and preserve real ends

`metadata_save.rs:1911–2095, 2197–2221, 2328–2392, 3050–3054` has multiple producers feeding the shared retraction; replacing one call in the collision path alone is incomplete. Carry explicit lifecycle/ownership semantics to the board operation rather than inferring authority from `purged`:

| Producer or caller | What it owns / required disposition |
|---|---|
| `Abort` | Incomplete join, possibly only prejoin; promote any exact retained Member withdrawal and purge its owned partial state. Reversible local board cache retraction, never whole-room end. No journal and no owned stored incarnation must not delete an existing room. |
| `AbortCompleted` | Current code purges a completed join under exact wrap/instance/epoch fences. Revised behavior classifies commit evidence first: uncertain/lost Accepted uses the retained own withdrawal and newer retry; a verified durably accepted obligation remains resumable and is not silently purged/withdrawn. Only explicit authorized cancellation removes that owned construction state, preserving continuity. |
| `RejectCreated` | Rejects creation owned by that attempt; may queue a signed **Room** withdrawal when its created room was exposed. Remove the failed creation's owned local cache without conflating an arbitrary transient purge with a real room end. Preserve its legitimate signed withdrawal and existing durable publication/authority semantics; when a genuine signed end is verified, terminal behavior remains. Do not drop it or silently reinterpret Room as Member. |
| `PurgeUnpublished` | Removes only the owned unpublished incarnation after rejected publication, under its existing authority fence. Reversible local retraction; preserve queued evidence and do not affect replacement incarnations. |
| `PublicationReject` | Member scope can call `queue_abort_join` and set `purged`; classify that branch as incomplete join, not end. Other branches build and retain the requested signed withdrawal without necessarily purging; preserve scope, route, durability and actual end semantics. The preceding rejection-stage immediate `retract_live_channel` must receive the same classification, not only the later journal install. |
| Rejected existing open | Retract only its live projection and reversible board cache, retain stored rows/open intent and current policy refusal. Later authorized open must succeed without restart and without weakening policy. |
| Genuine local end / received signed Room withdrawal | Remain terminal: `actor.rs:20605–20644` calls `forget_room_on_board` when genuinely ended here; `nat/service.rs:1539–1600` verifies authorized Room withdrawal and calls `withdraw_room(..., Some(signed_wire))`. Never route either into the reversible path or clear their negative state on a retry. |

In particular, `RejectCreated`'s signed Room withdrawal for an exposed failed creation and actual terminal room-end authority require careful separation by the real signed lifecycle and existing contract. A local reversible cache operation cannot cancel a signed Room withdrawal already accepted by other boards; an implementation must retain and honor that fact rather than promise this created room can be retried as a live room. This differs from joining an already valid target room.

#### Bounded corrective design

### 1. Reversible local cache retraction, not a tombstone reset

Introduce a distinct board-store/network operation for removing this node's transient room projection and cached discovery data without creating or deleting `withdrawn_rooms`; use it only for the classified transient paths above. Continue existing actor cancellation, route/membership clearing, ownership/incarnation fences, journal recovery, revision notifications and expiry bookkeeping. Its exact field list must be reviewed against the existing eviction and service machinery; it must not be a copy of `withdraw_room`: that function also deletes `withdrawn_members` and `member_withdraws` (`store.rs:430–437`), which are independent signed negative evidence. Preserve those, relevant pending withdrawals and admission/key material needed to validate them, as well as any genuine existing room-end marker. Remove or unpin only appropriate live/cache records, with coherent genesis count/source/revision bookkeeping.

A temporarily removed genesis is no longer a locally pinned held room. Preserve `serve_rooms` / `may_anchor` policy for an unpinned remote genesis; do not relax the service gate or let a remote peer manufacture membership merely because cache was removed. A legitimate subsequent join/open may locally republish and pin its validated genesis through existing authority; received signed Room withdrawal and actual ended-here state still win.

Member withdrawal is timestamp-scoped, not a toggle. Keep `withdrawn_members` and signed `member_withdraws`; `accept_notice` processes pending withdrawal before notice and rejects a notice at or before the newest withdrawal, and ordinary records at or before it are refused (`store.rs:499–511, 568–631`). On retry, an authenticated later admission/record must be strictly newer under existing clock-sanity and authorization rules; never delete negative evidence to make it pass. If a retained/replayed withdrawal is equal to or newer than the new witness, fail closed and report recovery required rather than fabricate a later signature, override a clock check, or silently accept. After restart preserve/recover the existing durable journal and re-establish relevant signed evidence through the existing board protocol; neither assume all in-memory board evidence persists nor use restart as repair. Validate replay of an old withdrawal after retry and across restart: it must not erase a genuinely newer authorized admission, while an equal/newer valid withdrawal must still refuse stale records. This is a required design/test boundary, not a claim that current persistence already satisfies it.

### 2. Authenticated preflight and real namespace reservation

After mutual PAKE, proposal v2 binds canonical name and own-history classification with the exact schema/domain in ADR-023 RL-8.7 and ADR-008 LS-21c. Its unsigned array is `[2, channel_id, epoch, joiner_id, responder_id, timestamp_ms, room_name, own_history]`, signed under `vox/join-admission-proposal/v2` plus NUL. Null/invalid names refuse before Prepared; own-history is a tagged absent/head/known-unavailable result, with supplied own Public heads independently verified. Accepted no longer carries an unsigned name. Obsolete v1 proposal/Accepted formats receive truthful update refusal, not a downgrade; a post-Prepared malformed/lost Accepted remains commit-uncertain.

Before Prepared, the joiner's actor atomically reserves the authenticated name against held rooms and pending create/join/rename. Release aborted pre-accept reservations only with their owned cleanup; a durably accepted obligation keeps its reservation across crash/lock until commit or explicit cancellation. Preserve same-ID idempotence and the unrelated same-name room. Late authenticated rename uses the by-ID completion rule, not a new responder erasure authority.

### 3. Proposed post-admission completion, not new cancellation authority

The proposed ADR-023 RL-8.7 now chooses the preliminary Opus review's simpler alternative: after successful authenticated name preflight and remote admission, a later authoritative rename clash completes the join and displays both rooms by ID, with an explicit ADR-028 R-3 exception. It does not add a responder's unilateral authority to cancel another author's committed admission. Preflight collisions still fail before admission and preserve the original room.

Distinguish three durable boundaries. Before AdmissionPrepared, abort reversible local work. After Prepared but without verified Accepted, commit is uncertain: promote the pre-journalled own Member withdrawal, warn that remote admission may have occurred, and require a strictly newer fresh PAKE retry. Only after verified Accepted persist the proposal, final witness, verified genesis, exact name reservation and existing double-lock SEK wrap in the join journal before later checks. Generate/seal that wrap before Prepared if needed so a crash cannot lose the accepted construction material; never retain the passphrase. Restart asks the operator for the passphrase, verifies the retained wrap and resumes that accepted witness without a second admission or rollback withdrawal. An unpersisted/lost Accepted is uncertain, not magically resumable. Retain accepted reservations through crash until commit/authorized cancellation; pre-accept abort releases its own reservation. Current policy/removal checks still win. No new responder erasure authority or blind Departure is introduced.

#### Acceptance and safety inverses — required future proof, not results

Use actual product/daemon consumer journeys with separate scratch DATA, CONFIG and HOME per synthetic identity; no live operator profile, trust alterations, borrowed identities, credential inspection, or history/counter clearing. Extend existing journeys and exercise exact observable new messages and rosters, not just command exits or board internals. Distinguish pre-commit refusal from post-commit retained completion honestly.

1. **Wrong passphrase then right**, same daemon and room: failed attempt followed by correct join without restarting; both directions read distinct newly posted messages, host roster is truthful, no reapproval. Include failures before proposal, after proposal/prepared, and failure paths selected by real lifecycle boundaries; prove no prior failed join poisons the target.
2. **Collision:** distinct same-name rooms; refusal leaves the unrelated room and its data/communication intact and does not create a remote governance member. Resolve the name conflict through an authorized action, retry in the same daemon, verify exact new messages read both ways and accurate membership. Exercise concurrent create/join/rename reservation races and name changes after preflight; no name leakage to unauthenticated wrong-passphrase peer.
3. **Policy-rejected existing open:** induce real authority/policy publication rejection of an already stored room, verify it stays closed and stored while policy denies it, then restore authorization and open on the same daemon; prove two-way reading and unrelated room intact. Do not weaken the policy or discard stored data.
4. **Terminal inverse:** a genuinely ended-here room and a valid signed Room withdrawal remain terminal while their valid evidence is retained/available; local cache retraction and stale records must not defeat it. The board is RAM-only: do not claim unconditional restart terminality from its tombstone. Preserve member negatives, timestamp and pending-verification semantics. Lost evidence in staging is APPARATUS, not proof of a durable guarantee.
5. **Post-admission boundaries:** force a late rename and observe completed by-ID join. Lose Accepted after Prepared and observe explicit commit uncertainty, own withdrawal and a newer fresh PAKE retry—not “resume” without a witness. Separately persist verified Accepted, fail later construction/publication, restart, re-enter the passphrase and resume that exact retained witness/wrap/reservation without another admission. Explicit cancellation publishes its own Member withdrawal; neither crash nor child disconnect is implicit cancellation. Preserve original rooms, signed history and truthful rosters/status.
6. **Independent consumer-sensitive red mutant:** the actual end-to-end journey must fail if reversible retraction is replaced by the old terminal `withdraw_room(..., None)` behavior, or if an induced committed-admission failure is falsely reported as no admission/completed local success. Internal-only assertions, mock echoes, successful post exits and computer-confirmed badges are insufficient.

Existing `paired_ready_nodes_read_both_ways_and_survive_reselection` covers ordinary pairing and reselection, not these failed-join, namespace, reopen, terminal and admitted-completion boundaries. Extend valid consumer journeys rather than relax those boundaries.

#### Unresolved choices and handoff

Independent ADR review must settle exact signed-proposal version/absent-name encoding, crash-safe namespace reservation ownership, retained post-admission completion and precise reversible cache fields. The proposed RL-8.7/R-3 late-rename exception replaces the earlier unapproved responder-cancellation idea; no new cancellation authority is proposed. No profile reset, restart workaround, fabricated time, trust expansion or history deletion is authorized. This artifact makes no implementation or acceptance claim.

#### Corrective acceptance boundary

ADR-038 FX-32 requires verified recovery, continued reading and writes resuming only once the author feed is current. A supported leave/rejoin must not manufacture a conflicting prefix. Recovery must establish the author's existing signed history before any new signed author entry, including implicit control/key entries; normal new-member admission must still work, and genuine older-backup/fork refusal must remain.

The operator explicitly selected **Retain continuity marker** after the erasure-versus-safe-rejoin tradeoff on 2026-11-06. The narrow Leave exception retains only the last own signed history head (existing recovery-head type with room/author binding) and highest authored sender chain/generation. Derive the append frontier during verified recovery; retain no message body, room name, passphrase or sender/Drive secret. Persist continuity with committed author state before external publication, including final leave. A failed save prevents publication and successful Leave; End erases the Leave-only marker. The product choice is approved, not the technical implementation.

Rejoin installs its recovery fence before empty-head initialization or any authored entry. The revised RL-8.5 explicitly gives a verified durable admission notice newer than departure limited recovery standing before return Presence, propagated/restored through existing notice machinery. Peers honor it for own-head/pages, own-generation recovery and otherwise permitted key redelivery; it does not override trust, consent or a validated admin removal. Recovery verifies the retained head and derived frontier, reconciles higher heads and obtains applicable key material before generation advance and return Presence. Discovery and independently authorized reads remain available; show exact pending/integrity limitations rather than promise blocked sync still works.

The operator subsequently chose automatic legacy fallback: “it should be automatic and just start with no history if it can't derrive”. For an unmarked binding, try authenticated recovery; when no prior authored history can be derived, start empty without confirmation or blanket legacy read-only behavior. Never discard a known signed head, retained marker or conflict to force fallback; malformed/refused/contradictory evidence is not an absence result. The admitting member checks prior authored history and discovery hints, returning RL-8.7's authenticated classification. Its absence assertion is not global proof; release notes disclose residual risk from erased/withheld history. Existing forks stay write-frozen with honest permitted-read limitations and an explicit new-identity remedy, never automatic reset or peer-history deletion. The technical v2 classification still requires Opus review.

Extend the existing real-binary `a_node_leaves_a_room_proof.rs` journey with this current-version retained-history staging and bidirectional distinct messages. It is already a valid consumer proof; absence of internal-counter assertions is not a defect in that proof. Its claim that catch_up_generation is the relevant mutation hook must not be assumed current: LSP currently finds that symbol's definition but no caller.

Historical #1024 (`robertelee78/vox:ADR-038:S8:own-feed-recovery`) was explicitly retired as Won't do for old-room follow-up, with new current-contract reports directed to new scoped issues. This newly created current-version room is not that retired migration scope. No reopening, implementation attempt, accepted candidate or published repair is claimed here.

#### Causal chain and effects

1. `room_map.rs:12–18,157–186` resolves a start directory using the deepest applicable block, with linked worktrees falling through to their main repository. `ask_directory` at 214–231 returns the **resolved block's directory** whenever there is a match, not necessarily the actual repository containing the session. 2. `room_ask.rs:33–94` examines interactive known-harness registrations with a start directory. A `room none` match suppresses the ask. For a room match, it asks when the node is outside that room, unless the session was moved elsewhere; it groups by `ask_directory` and room. `host.rs:2068–2097` determines outside from attached-node held rooms and join status; an in-progress retry after a prior failure does not hide the ask. This is derived from map and registrations, not a single dismissible invitation.
3. `RoomAsk.swift:36–57,69–75,114–116` offers Join It for a bound ask and offers Not This Repo only for an empty `ask.room`. Interactive dismissal is disabled. Choose Another Room opens the form and Back returns to the same choice. `NodeModel.swift:2317–2332` sends an empty-link bind for Join It; `host.rs:2114–2135,2148–2196` finds a pending ask, reads its mapped link and secret, and returns `done: false` on failed join. The UI calls `finishRoomAsk` only on success (`RoomAsk.swift:155–172`), so a failed join leaves the user without an opt-out.
4. A UI-only button cannot fix this. Existing native decline reaches `VoxClient::decline_room` (`crates/vox-ffi/src/client.rs:5244–5250`), `DaemonRequest::RoomDecline` (`daemonipc.rs:385–389,1266–1267,1482–1484`), and `host.rs:2265–2288`; `room_map::decline` (`room_map.rs:394–409`) deliberately refuses an **exact** existing block, returning unchanged. A bound ask's directory normally names precisely that block, so the backend refuses it too.
5. `NodeModel.swift:2234–2258` refreshes the current ask or retires it if the daemon stops reporting it, except while a bind/decline operation is active. Source does not establish a separate failure of retirement after successful membership. Leaving a room is not declining a map: a mapped node outside the room can be asked again; leaving also has membership/history side effects unrelated to the requested repository decision. Failure is not authority for an automatic unbind, trust change, room leave, history deletion, or retry loop.

The map is shared by every node in the data root and holds a link and potentially a passphrase (`room_map.rs:1–18`). Replacing the exact bound block with `room none` removes that block's saved credential; other blocks must remain intact. That change controls future session selection for the affected scope across harnesses and nodes, not existing sessions' current room. The operator must be told that credentials will be needed to bind again, that the action does not leave a room or alter global trust, and the exact directory/worktree inheritance scope and explicit overrides. Do not show or log the credential.

#### Existing authority and rebind contracts

ADR-029 RB-2, RB-4, RB-6 and RB-7 (`docs/adr/ADR-029-sessions-and-the-repo-room.md:184–195,214–229`) specify deepest/worktree lookup, lifetime stability of session room, operator-owned binding with secret entered outside the agent, and canonical `room none` with later bind replacing it. There is no need for another suppression/state database.

The existing agent path is materially different from operator replacement. `agent_room.rs:106–140` accepts a registered session's start and calls shared `room_map::decline`; an agent may run `vox agent room --none` under RB-7. Current `decline` only checks exact blocks, so an inherited parent binding can already be shadowed by a new no at the start directory. Globally changing it to replace a bound block would additionally permit destroying the exact operator binding and saved credential. Preserve the unbound agent-decline use case but refuse an agent decline that would replace **or shadow any resolved room binding**; check atomically against the actual resolved state. Explain the operator-only action instead. `coord::agent_marked` at `coord.rs:207–218` treats nonempty harness marks, even malformed ones, as marks; apply that LT-8 pattern to any operator CLI replacement route rather than treating a terminal flag or session name as authority. This constraint includes a registered agent-marked `--none` against exact and inherited bindings.

A deliberate terminal rebind already exists in source: `vox room join <link> --node <node> --bind <dir>` canonicalizes a real directory (`room_cli.rs:5625–5654`), authenticates the supplied passphrase even for an already-held room (`5675–5694`), joins otherwise (`5726–5764`), and uses `room_map::bind`, which replaces an exact `none` or binding. It does not require a pending ask. This is a source-established CLI path, not an exercised acceptance result, and it is not by itself an app-usable recovery. `host::room_bind` requires a current ask before doing anything (`host.rs:2114–2118`), while `room none` suppresses asks (`room_ask.rs:55`): after decline, the current native ask flow cannot deliberately rebind. Existing `room_map::bind` does `drop_block` then `add` in separate writes (`room_map.rs:417–438`); it is not an atomic replacement and is not a safe template for the new operation.

#### Proposed bounded fix

### 1. Explicit, scoped operator decision

Expose an operator action on a bound native ask, with a confirmation that names the actual target repository, the affected inherited scope and the room/binding being changed. State: future sessions in the chosen scope across all harnesses and nodes of this data root no longer automatically bind or ask; existing running sessions are not moved; no room is left and no global trust is changed; replacing a block discards its saved link/passphrase and later rebinding needs room credentials. Explicit more-specific blocks and unrelated bindings remain effective. Cancel changes nothing. Failed Join It must continue to show its real failure, not implicitly opt out.

For an exact repository block, operator confirmation replaces that exact block with `room none`. For a binding inherited from a parent outside the current actual repository, **do not replace the parent**. Derive a canonical current-repository boundary from the registered start independently of `ask_directory` (including the linked-worktree-to-main mapping), validate it is an appropriate directory and that the displayed registration actually resolves through the shown parent, then write a more-specific `room none` at that repository boundary. Linked worktrees falling back to that main repository inherit the no unless a more-specific worktree/block overrides it. This preserves the parent's credential and other repositories' traffic. A bound ask currently groups sessions by the parent block; split/re-express asks by actual repository decision boundary so one click cannot silently affect sibling repositories, and explicitly identify any sessions outside the selected scope.

Where a real current-repository boundary cannot be validated (including non-repository directories, stale/missing registration paths, ambiguous worktree metadata, or a scope already controlled by a more-specific override), do not silently choose the parent or an arbitrary start subdirectory. Require an explicit operator choice of a clearly described valid boundary or offer cancel; if the product cannot establish such a boundary, fail safely and explain the unresolved choice. The exact presentation of that fallback is a remaining design decision, not permission to mutate the parent.

### 2. Atomic, stale-safe update, not global decline semantics

Add a distinct operator replacement operation, not a new meaning for the shared agent `decline`. The displayed ask must carry an opaque, non-secret snapshot identity for the target scope and actual resolved block, including enough state to detect a changed link or credential even when room ID is unchanged. The daemon may retain the snapshot in memory or use an authenticated opaque token; never expose a raw credential, a guessable password-derived digest, or secret-bearing map text through IPC, UI, logs, or error messages. Include the target repository boundary, source block identity and scope in the snapshot. A daemon restart or lost snapshot makes the answer stale, not an unconditional write.

Under a data-root-wide interprocess room-map writer lock, re-read and parse the current private map, re-resolve the registered start and repository boundary, and compare the entire expected effective block and target override state with the snapshot the dialog actually displayed. If either changed, the registration/boundary is no longer valid, or a competing explicit block appeared, return a truthful conflict and refresh the decision; do not apply it to the newer state. Check and single durable private-file replacement must be one serialized transaction: construct the complete result in memory, preserve unrelated blocks and their credentials/comments, write mode 0600 to a unique private temporary file, flush and atomically replace the map using the repository's durable-write conventions. Report failure without claiming a no was saved; if rename succeeded but durability reporting fails, re-read and report uncertainty rather than asserting no change. Avoid exposing a transient missing block. All Vox writers—not just the new route—must participate in the same cross-process lock and whole-map update protocol, including `room_map::add`, existing agent decline, `bind` callers in `room_cli.rs` and `host.rs`, and the `agent_room.rs` offer-save path. The shared agent decline must check effective inherited state under that same lock, while retaining permitted no-on-unbound behavior. External manual editors do not participate in a Vox lock: compare the current file immediately before replacement and surface conflicts where detectable; document that arbitrary concurrent noncooperating writes cannot be serialized by an advisory application lock alone.

The operator-only boundary must be enforced at the actual public entry points, not merely by hiding a Swift button: reject `coord::agent_marked()` for any CLI replacement entry, including malformed nonempty harness marks, and use the established operator-native route for an explicit app action. Keep agent `--none` on its non-destructive path. The existing daemon request carries only a directory and cannot prove the caller's environment or that a person confirmed a particular binding; do not claim that adding a new IPC verb alone authenticates a human or defeats a local process capable of arbitrary same-user socket access. The implementation/design review must establish the existing local IPC authority boundary and prevent ordinary agent-facing command/FFI paths from invoking replacement as an agent; if the existing protocol cannot enforce the required boundary, add an appropriate operator authorization mechanism before exposing the mutation rather than relying on caller-supplied `operator=true`.

Propagate the snapshot, selected scope, conflict result and explicit confirmation through `room_ask.rs`, daemon `RoomAsk` and request/frame encoding/decoding in `vox-core/src/node/daemonipc.rs`, host dispatch, `vox-ffi/src/client.rs` UniFFI records/methods, `NodeModel.swift` and `RoomAsk.swift`; update TUI/status representations and answer guidance where their current grouping or commands would misstate the boundary. Preserve unrelated consumers and protocol compatibility according to the project's actual versioning contract. Retire a dialog only once a successful write is acknowledged; refresh stale/conflicting state without presenting an old confirmation as valid. No source-text-only gate is an acceptance substitute.

### 3. Native deliberate rebind after a no

Add an explicit repository binding entry point in Vox.app independent of a pending ask: select the repository/directory, show its currently resolved decision and precise effective scope, then choose an existing room or enter its link and type its passphrase in the app. Confirm who can read the saved credential. Reuse the real authenticated join/passphrase-check behavior: authenticate even for a held room, join required selected nodes as appropriate, and only then atomically replace the intended exact `none`/binding using the same stale-safe map transaction. Refuse a stale scope, bad credential, unavailable node, or write failure truthfully; do not erase the no on a failed attempt. Report any actual partial node joins if a multi-node operation fails; do not claim all-or-nothing room membership where joins already succeeded. No secret is sent through an agent session.

This deliberate rebind controls future registrations; it must not silently move already-running sessions. A separate explicit session-move action may retain existing behavior and existing ask-answer flows may preserve their own documented waiting-session behavior, but the no-to-bind operation itself must not conflate future map selection with moving a session. Native rebind must be reachable without deleting a block by hand or generating a new ask and must not produce the same prompt loop. Keep the existing deliberate operator terminal `--bind` usable and migrate it to the same atomic writer; use it as an additional rebind route, not the sole app answer.

#### Coverage gap and actual-user acceptance to plan

`VoxAppProofs/FirstRunProof.swift:3528–3541` exercises Not This Repo for an initially **unbound** canonical repo and later worktree; it does not exercise a bound prompt, failed Join It, replacement of a credential-bearing binding, inherited parent scope, or rebind after `none`. Existing terminal/agent-hook coverage of the ordinary decline cannot establish native operator authority or a bound-flow escape. Existing room flows are not proof of the reported native interaction.

Acceptance must use actual native Vox UI and real product behavior with separate scratch DATA and CONFIG roots, synthetic identities and credentials, not the operator profile, mocked callbacks, internal string-only assertions, or hidden configuration copies. At minimum:

- Start with a bound repository on a node outside the mapped room, make Join It actually fail, observe its truthful failure and choose the explicit native opt-out. The dialog closes after durable success; next relevant session and linked worktree turns do not prompt, including after ordinary app/daemon lifecycle as applicable. A failed join alone changes neither the binding nor trust.
- Confirm scope: all harnesses/nodes following the affected binding respect the no for future sessions; already-running sessions remain where they were. For a parent binding shared by two repositories, opt out one actual repo and verify the sibling still resolves/joins/communicates and the parent credential remains usable; explicit nested/worktree overrides stay intact. Observe real room traffic, not just map text. No room is left, trust widened/removed, unrelated block or history altered.
- From a registered agent-marked process, `vox agent room --none` cannot replace an exact operator binding **or shadow an inherited one**, and cannot destroy its credential; an unbound agent no still works. Exercise stale confirmation versus changed room, changed credential with same room, and a newly created override; the older decision must conflict without overwriting the newer state. Exercise competing cooperating map writers and write failure/uncertain durability without a false success or lost unrelated block.
- After a successful opt-out, use the app's deliberate rebind entry without a pending ask; authenticate the real credential and verify a new session/worktree uses the selected room without a prompt loop. Wrong credentials leave the no intact. Separately confirm the existing operator CLI bind path still replaces a no and checks held-room credentials. Verify that deliberately rebinding does not silently move existing running sessions.
- Inverse safety: genuine explicit overrides, unrelated bindings and room communication remain usable; no automatic unbind on failed join, no unauthorized agent replacement, no credential exposure, no hidden leave, and no global trust change. Include the invalid/ambiguous repository-boundary refusal and a refreshed stale-dialog case. Native observable outcomes are decisive; disposable source/mechanism spikes may supplement them, but no unit or in-process library tests are permitted.

#### Remaining decisions and dependencies

- Product/design review must settle the exact fallback UI when a valid distinct current-repository boundary cannot be established, without implicit parent mutation. It must confirm the concrete entry point for native rebind and wording of the displayed affected scope.
- Security/design review must specify and verify the operator authorization boundary for same-user daemon IPC and agent-marked processes; environment marks on a CLI alone do not authenticate IPC clients. Resolve before claiming operator-only enforcement.
- Select a snapshot representation and durable-write/locking implementation consistent with actual daemon lifecycle, protocol compatibility and supported filesystems; specify how noncooperating manual writes and post-rename durability uncertainty are reported. This is a map transaction, not another persistent state database or a retry framework.
- ADR-029 RB-5a/RB-6/RB-7 and relevant ADR-031 repo-ask/operator-authority text and app/session guidance require coordinated updates to express bound opt-out, inherited-scope protection, no implicit moves, and native rebind. The parent owns those changes and tracker writes. Independent document review and post-execution review remain required; this artifact is not their verdict.

## 5. False join notifications

### False join lines: source-bound RCA and repair design

#### Symptom, evidence and limits

The operator's screenshot/report is ground truth that Vox displayed apparent fresh join lines for members already present, including working-directory wording. Do not reinterpret the screenshot as proof those people actually rejoined. The exact ordering of asynchronous Swift reads at screenshot time was not logged, and the screenshot alone does not establish which of several possible roster timing paths occurred. The source defect below is established; applying that precise interleaving to the screenshot is a causal inference, not a runtime trace or a reproduced screenshot. This investigation did not run the app, mutate profiles or exercise a native journey.

Source inspected: `/private/tmp/vox-20261106-incident-corrections`, at the supplied source binding `ec00fa91bbc3ad3c48aa5535f65d72decdd83689`. The incident's installed Vox 0.4.19 helper is bound in `rca.md` §2 to SHA-256 `e4046e3206340a0829da68079983fb52db556c57b0ca9c75d49156f3296c29ad`; that binding does not log the Swift task ordering. Existing `next-repair-plan.md` §2 calls for populated, actual-new-member and genuinely-empty-baseline cases. `local://vox-omp-rca-delivery.md` likewise identifies the watcher/initial-baseline race as source-established and the screenshot interleaving as inferred. No authentic admission timestamp is established by the current displayed line.

#### Exact ownership and failure chain

All source paths below are relative to the bound tree.

1. `apps/macos/Vox/NodeModel.swift:1862–1870,1898,1928` changes selection, empties `joins` and resets `members = []` when opening a different room. That array is presentation state, but no separate flag says whether a successful roster has ever been published. A same-selection `select` returns early (`1865`); it is not necessarily a new baseline.
2. `NodeModel.swift:1954–1974` starts `watchReads(id)` before the ordinary `show` performs its initial async reads. Initial `memberRows` is read only at `1989–1990`; more awaited reads follow, and its `members = rows.rows` is not published until `1996–2019`. Guarded selection/generation checks protect against an old room being drawn under a new one, but do not order two valid reads for the same room/generation. `memberRows` (`3484–3505`) obtains roster and consent and filters out the local node, so an empty peer roster is a valid successful result, not evidence of loading.
3. The watcher (`3664–3683`) starts with a two-second sleep, then reads a roster. It awaits further work before committing, with cancellation/selection/generation/epoch checks (`3684–3703`). If this reaches `3718–3734` before initial publication, the current array is empty even if existing remote members have long been present. Every returned peer is therefore in `came`. The condition `!before.isEmpty || !came.isEmpty` is true when a populated roster follows that empty array, so it appends `JoinLine` objects at local observation time. A slow initial page or later awaits permit the interleaving; two seconds does not guarantee initial publication first.
4. The later initial publication writes `members` directly without removing those ghost lines (`2017`); it can also overwrite a newer watcher snapshot in the same generation. Conversely a watcher that read an older snapshot can commit after a newer initial publication. Selection/generation guards do not detect either same-generation reorder. A simple boolean that only suppresses the very first watch's announcements without coordinating all writes would still allow stale roster regression and later duplicate/false changes.
5. `NodeModel.swift:3737–3757` refreshes each existing line's caption via `client.joinSaid`; `Timeline.swift:80–82` inserts nonempty join captions into the timeline at the locally generated `at`. `crates/vox-ffi/src/client.rs:7110–7161` builds text from current membership and current trusters, not a recorded admission event. It requests current `SessionJoin` (`7162–7184`) and, if a drive-readable open Session has a cwd, adds its current directory (`7186–7214`). Its instance/authority checks and current-membership check are important privacy and correctness protections, but do not establish a historical join or that cwd was present at admission. `sessionsChanged` clears potentially private old wording before suspension and can refresh captions (`NodeModel.swift:4433–4453`); it does not independently create a join.

#### Why existing guard and coverage do not fix it

Requiring `before` to be nonempty suppresses ghost joins but also loses the first genuine peer admission following a successfully observed empty roster. An empty array cannot encode both unknown and known-empty. The local-node filter makes that inverse realistic. The watch scope guards stale selections/observation epochs, not concurrent same-generation roster ordering or an authoritative baseline. Caption read fencing prevents stale/private wording, not false line creation. A successful initial `show` and a two-second interval likewise do not guarantee their order.

The existing real-product native journey `apps/macos/VoxAppProofs/FirstRunProof.swift:6382–6430` opens mission, subsequently admits the synthetic remote Dave, and asserts his join text and truster. It is a useful positive, but it does not assert the absence of join lines when an already-populated room first loads; it does not prove known-empty→first join or room-switch in-flight behavior. It must not be cited as proof of those negatives. Existing duplicate fingerprint suppression (`NodeModel.swift:3731`) prevents a second currently retained line, but does not make its first creation truthful.

#### Bounded repair in the existing Swift model

Use minimal generation-scoped roster observation state in `NodeModel`, not a second event system or fabricated admission history. Distinguish `unknown` from `known` (a successful published snapshot, including `[]`), and track a small publication revision/token to fence competing reads. Bind the state to selected room, `roomReadGeneration` and `nodeObservationEpoch`; also invalidate it when the saved-room instance is replaced even if the displayed room ID remains the same. A newly selected/replaced room and restarted observation start unknown. Keep actual visible/recovery snapshot behavior as required, but never treat retained rows from an old owner/instance as a baseline for the new one.

Route both successful writers—the initial/refresh `show` publication and `watchReads`—through one MainActor-owned roster commit path. Each captures the baseline publication revision and the existing room/generation/epoch/instance authority before its async roster read. Commit only if the owner/instance is still current and no later competing roster publication has invalidated that read; discard/re-read an obsolete result rather than rolling membership backward. Preserve `show`'s joint page/inspector and reconnect readiness boundary: if its roster is obsolete, retry/reconcile the authoritative page and roster rather than publishing a stale inspector or falsely marking recovery complete. The existing watcher start sites (`show` at 1971/2045, `readNewOnScreen` at 1308, `resumeAfterUnlock` at 3935) must all use the same state and fence; do not rely on only moving one start call. Ensure saved-room replacement detection uses the existing room-instance/observation authority, not room ID alone, including when `readNewOnScreen` changes `roomInstance` (1294–1296). All await boundaries need revalidation before publication.

On the first successful current snapshot, seed the known baseline and publish members/trust/presentation but create no join lines, whether it is empty or populated. A failed read must not seed empty or replace good rows. For every later successful ordered snapshot, compute additions by fingerprint against the previous *known* snapshot, remove lines for departed fingerprints, and append at most one line per newly observed fingerprint; update baseline even if rows compare equal or only metadata/trust changed. Both writers must use this same logic so a refresh cannot silently consume a real addition or cause a later fabricated one. Preserve existing caption refresh and explicit clearing on lost authority (`3743–3763`, `4433–4453`) and make stale caption callbacks unable to write across a generation/instance change. Scope/recovery cleanup at selection, `releaseHistoryViews`, observer restart and unlock must reset/fence the baseline consistently; reconnect does not invent joins for changes that happened while observation was unavailable.

This is a roster-difference observation, not a durable admission event stream: an admission before the first successful baseline, or a join and departure wholly between polls, cannot be reconstructed from snapshots and must not be asserted as an exact admission time. Do not change trust, admission, drive permissions, FFI authorization, session cwd privacy or room identities to mask the symptom. No product edit is made in this investigation.

#### Acceptance and safety inverses

Extend the existing native real-product journey rather than introducing a separate framework. Stage all nodes under isolated data/config/home and private test credentials; do not run it against real profiles. Use actual UI-visible timeline lines and authoritative fixture membership, bounded waits and a controlled read-delay/interleaving seam where needed; do not infer absence solely from a successful setup or a short arbitrary sleep.

- Open a room already containing multiple remote members, force the watch to obtain/publish its successful roster before the delayed initial page/roster publication, and wait through a completed watch/refresh. Assert the actual populated roster is visible and **zero** join lines for those preexisting fingerprints. Release the delayed initial response and assert it cannot regress the roster or create lines. Include the opposite completion order.
- After the populated room has a known baseline, admit one distinct remote member through the actual product. Assert exactly one correctly attributed visible join line, no spurious lines for existing members and no duplicate after subsequent refreshes; preserve existing caption/trust behavior and verify no cwd appears without current drive authority.
- Establish a successfully observed genuinely empty *remote-peer* roster, then admit the first peer. Assert exactly one line for that peer; this explicitly rejects the tempting `before.nonEmpty` workaround. Verify a failed first roster read followed by a populated successful read remains unknown until success and creates no ghost lines.
- Hold an old room's roster or caption response in flight, switch to another populated room (and separately replace/reopen the same room ID with a new saved-room instance), then release it. Assert no old-room member, line or private cwd appears in the new owner, no stale roster overwrites the new baseline, and a subsequent genuine admission to the new baseline is still reported once. Include same-generation show/watch reordered snapshots and observer recovery/epoch invalidation; stale results must not clear genuine members or generate a false rejoin.
- Demonstrate the negative controls are consumer-sensitive: the pre-fix watcher/interleaving produces the populated-load false line, and a `before.nonEmpty` inverse fails the first-genuine-join case. Retain existing native join/caption positive assertions. Do not relax identity, trust, admission or privacy checks.

These are proposed acceptance criteria, not executed tests or evidence of a repair. No UI tests, builds or app mutations were run during this investigation.

#### Bounded fix design and component ownership

* **OMP adapter and native lifecycle:** Make the exact current TUI main session/generation the sole registration authority. Track `unregistered`, `pending`, `registered`, and actionable failure for that generation, not a process-wide success boolean. Subscribe on startup and switch/branch/tree, reconcile the live manager ID before any attempt and before using a receipt, retire old routes on actual change, and recover safely if a transition is cancelled or rolls back. A target observed only during a provisional switch must not remain authorized after rollback. Ensure an older child completion cannot overwrite a newer generation or revive a retired route. Retain existing transition fences and route-token authentication.
* **Truthful existing receipt:** Independent Opus source review found no need for a new format or daemon IPC. Register-only already returns success only after a non-Attaching SessionRegistered. The receipt is that child's exit 0 while the captured generation remains current; `hook()` already enforces this fence. Track and use that outcome instead of swallowing it. Ordinary hook success, staged cold start, Attaching, timeout, missing node, failed socket or EOF is not registration. Capture bounded sanitized stderr and show actionable failure without endpoint tokens or private content.
* **Recovery ownership:** Activation and actual prompt/use coalesce the existing register-only child for the current generation. A confirmed pre-envelope missing-registration failure returns it to unregistered. Idle recovery needs the proposed narrow Vox-native availability-watch bridge in ADR-029 P420-OR-5: existing daemon Subscribe plus exact-node snapshots, bounded availability reconciliation/reconnect, typed transient failure pacing and no automatic attach/unlock or model call. A steady Ready node after a transient registration failure still needs a later coalesced attempt; do not require a fresh readiness transition or operator prompt. One watcher and one register child are bounded by the native Session lifetime, not a generic retry framework. A newly identified source race also needs mutation-time ownership: killing the old child/ignoring its callback does not cancel an already accepted daemon registration write. Serialize generation revocation with daemon writes, deferred completion and cold-start staging under the proposed private native ownership lock/lease; stale disk state alone is not authority. This is a new source-backed design awaiting Opus review, not an existing helper or observed race reproduction.
* **Post path and authorization:** Keep `coord.rs` native-marker, exact registration, harness and room checks intact; never auto-retry a rejected message under a different ID, write a second copy, weaken trust/room authority, or silently claim the prior post succeeded. After repair, a new user-requested post uses the original session's verified registration. Keep routing and registration scoped to the owning process/generation and ensure stale records are not a new authority to inject into another session.
* **Failed-prepare recovery:** Distinguish an unconfirmed delivery from a prepare that failed before an envelope or injection; retain the fail-closed boundary for genuinely ambiguous delivery, but do not let a transient missing registration permanently suppress later legitimate activation/use recovery. Recovery must establish a truthful receipt for the still-current native generation before preparing again, rather than blindly clearing poison, borrowing an ID, or introducing a fixed five-retry/backoff framework.
* **Tests/docs and product boundary:** Extend actual native OMP/Vox journeys with failed startup/prepare recovery, stale completion and switch/rollback inverses. A native session, real daemon and actual room post/read supply the verdict—not synthetic context, echoed ID or a registration file. Idle recovery additionally needs real room attention delivered after node/daemon recovery with no operator prompt. This is proposed design after a NOT APPROVED independent review, not an implemented or verified repair.

#### Native API, terminal consumption, and controls

At the referenced OMP source, `packages/coding-agent/src/extensibility/extensions/types.ts:2063–2087` exposes `sendMessage` for custom messages and `sendUserMessage` for a user prompt. Thus changing `sendMessage` to `sendUserMessage` alone neither proves authorized human origin, preserves deferred revalidation until consumption, nor supplies an operation-correlated receipt. It can also change interruption/queue semantics: choose and document the native behavior, not pretend each mode is identical.

OMP's extension context exposes `abort()` as an abort of the current agent operation (`extensibility/extensions/types.ts:773–777`). Meanwhile Swift presents Stop as ending the session and Interrupt as Esc (`SessionDrive.swift:115–133`). The former promise is false for this adapter; neither the abort request nor a generic later idle event proves a particular operation stopped. Slash is explicitly refused (`omp_mirror.rs:207–210,433–436`); approval/question controls follow the existing waiter path (`host.rs:2673–2703`), and no source here establishes an OMP-native external approval or question capability. Do not advertise successful support without an actual native mapping and receipt.

Tern is a native **presentation consumer**, not the authority channel. The actual Tern-side implementation and the installed IO OMP version remain unverified.

#### Bounded coupled repair

1. **Preserve the existing authenticated Drive authority and actor.** ADR-029 DR-1.2 explicitly lets a room member trusted with Drive type into the Session **as its operator**. Ordinary room questions, neutral attention notices and file contents are not explicit private Drive input merely because they came from the same node.
2. **Deliver explicit Drive under the original guard at consumption.** Retain the existing aside wake, context-time capability materialization and provider-marker observation. An idle Session starts a turn; streaming consumes at the next eligible step boundary. Do not eagerly call sendUserMessage or add an upstream API dependency. 3. **One operation identity and a defined response step.** Carry the unpredictable operation ID and authenticated scope through drive.id, bridge mapping, native receipt, drive-result.of and projection/UI; the private capability is separate and secret. Distinguish refused/not sent, bridge queued and native/provider accepted. 4. **Plumb eventual receipts end to end.** Publish a typed, bounded, ID-bearing extension event after the real acceptance condition, carry it via the authenticated mirror to a private session activity, extend projection/index/fold and pagination/reconnect recovery so later receipts associate with the same authored operation, expose structured FFI states rather than overloading `ok`, and have Swift update the matching send independently of subsequent composer sends. Do not manufacture “stopped”, “approved” or “answered” from sending a control frame.

#### Acceptance and safety inverses

Run in isolated scratch profiles, using the real Vox app/daemon, real OMP extension and a disposable actual OMP session; never reuse production messages or secrets. Exercise idle and actively streaming/tool-wait conditions. An authenticated operator sends a uniquely marked harmless question, sees the peer/operator provenance preserved, queue then exactly matched native acceptance, and only sees an answer if the actual native answer is demonstrably correlated. A second simultaneous operation and unrelated local user/agent turn must not receive the first receipt. Reconnect, pagination, compaction, branch/reset and late/out-of-order events must not misassociate or replay. A deliberately missing/ambiguous native acknowledgement stays unconfirmed even when a generic assistant reply exists.

Inverse cases: a spoofed actor field, ordinary room message containing instruction-like text, untrusted file/note, unauthenticated caller or peer lacking Drive must never acquire operator authority. An explicit Drive action from a Drive-trusted member remains permitted whether its caller is a person or agent; rejecting it solely as agent-origin would contradict ADR-029 DR-1 and the no-human/agent-typing ruling. Revoking Drive, removing membership, locking/replacing the node, switching room/history/registration/branch, or disconnecting before materialization must prevent disclosure/delivery under the captured guard; after the irreversible boundary report actual uncertainty rather than promising retraction. Verify at-most-once consumption, no cross-session targeting and distinct correlation for same-text messages. Abort must truthfully report request versus observed outcome, leave the Session open unless native termination is independently supported, and unsupported controls must refuse without effects. Capture only minimal sanitized operation IDs and transitions, not private reasoning. These are proposed acceptance criteria, not executed checks.

#### Native producer to Tern: what is actually being lost

1. OMP `packages/coding-agent/src/extensibility/extensions/types.ts:1242–1266` defines start with `args` **and separate optional `intent`**, update with `partialResult`, and end with `result` and `isError`. `lifecycle-mirror.ts:115–127,154–181` maps those events, including the background-wait `awaitingAsyncWork` distinction. The intent-tracing contract strips the injected intent from arguments before execution (`packages/agent/src/types.ts:473–477`); serializing args alone cannot reliably recover it. `message_end` is only one lifecycle event, not an entire transcript presentation.
2. OMP’s `packages/tui/src/tools/renderer.ts:11–60,101–153,162–181` defines a semantic tool head (title, target, path/link, metadata, badges, exit), body nodes, tone, preview/open/inline and actions, alongside contextual partial, execution-started, cancellation and host-capability options. Tool-specific `describeCall`/`describeResult` implement that contract; e.g. `tools/bash.ts:714–758`, `tools/edit.ts:1198–1204,1259–1266`, `tools/find.ts:365–387`. Custom extension hooks are arbitrary JS owned and run inside OMP, not an externally callable pure function promised by this type.
3. `packages/tui/src/chat/tool-execution.ts:1222–1255,1371–1419,1421–1476` chooses supported `tool` or fallback `card`, supplies live state, calls the selected custom or built-in describer, merges call/result as appropriate, and computes pending/running/done/error/cancelled. Describe exceptions use OMP’s generic presentation; images have their own path (`1492–1505`). Semantic content is not just prettified JSON, and a raw result alone lacks the whole component context. A `NativeChild` can itself be a live component (`packages/tui/src/native/node.ts:1–10,20–29,69–93`), so the TypeScript object cannot simply be presumed serializable or executed outside the host.
4. OMP produces described `k`/props/children via `native/describe.ts:15–27,40–62`, then stable identity and diffs through `native/reconcile.ts:1–24,254–277`; `native/backend.ts:1–19` manages surfaces, credits and blobs, while `native/encode.ts:1–11,23–26,94–95` frames TSP. The [Tern transport](https://docs.stencil.so/tern/protocol/transport.md) defines `q/o/f/b/...`, APC framing and negotiated chunking; [operations](https://docs.stencil.so/tern/protocol/operations.md) describes ack credits, coalescing, settle and bounded retention. Tern draws semantic nodes, e.g. Markdown, code, diffs and styled spans, not a copy of a raw ANSI terminal screen; `ansi` is a specific output kind, not the overall design. Native TSP capability-dependent fallbacks and Tern’s user-local fold state matter; TSP itself is not a proven Vox session export.

#### Vox loss chain and why existing guards do not repair it

1. `crates/vox-tui/assets/omp-extension.ts:609–645` publishes only text parts of user/assistant messages and stringifies tool args and results at start/end. It does not publish `event.intent`, subscribe to `tool_execution_update`, or carry non-text content parts or OMP’s semantic description. Async custom messages are outside the selected user/assistant roles; `agent_end` waits for `willContinue`/`awaitingAsyncWork` before emitting turn end (`647–655`), but waiting to end is not an async job presentation. JSON.stringify is a legitimate wire encoding for a structured object, but here the resulting string becomes the content and type/rendering information is no longer available downstream.
2. `crates/vox-tui/src/omp_mirror.rs:554–557,576–627` maps those strings to `input`/`output`, derives `summary` with `one_line`, and records success as `!isError`. `crates/vox-agentcomms/src/activity.rs:23–42` folds whitespace and cuts summaries at 160 characters; `54–99,103–109` splits one large string by serialized byte size into parts for later joining. This preserves long raw text when successfully carried, not native semantic structure, progressive updates or rich parts. A readable 160-character summary alone is not the renderer.
3. `crates/vox-core/src/node/session_view.rs:341–413` joins activity, folds `tool-done` into the call by reference, puts input/output into string details and constructs a single summary/status line. `crates/vox-ffi/src/client.rs:1239–1250` exports `line` and flattened `details`; `apps/macos/Vox/Sessions.swift:238–276,297–316` draws the tool as a one-line monospace `Text` with expandable monospace details. This explains the observed raw envelopes at every layer; changing Swift formatting cannot restore omitted intent, updates, branches or non-text values.
4. `omp-extension.ts:289–305,392–398,426–445` increments generation, clears tracked calls, closes followers and activates on switch/branch/tree; a subscriber receives current busy/name only, not an active-branch semantic snapshot. `59–81` fences reset/ancestry, and `500–545` reconstructs accepted wake history only. These fences protect current route and context; they are not a re-projection protocol that replaces stale visible branch history, reconstructs the current branch, or supplies missed tool progress after reconnect. The exact screenshot’s branch and connectivity state are unknown; this is a source/design gap, not a claim that a specific branch was wrong.
5. `omp-extension.ts:312–324` bounds output and disconnects oversized or slow followers. This prevents unbounded socket buffering but does not guarantee semantic catch-up or convey a complete oversized result. `activity::split` occurs only after a frame reaches the mirror, and thus cannot recover a frame rejected upstream. `SessionPages.swift:98–102` also accounts for line/details byte size, so structured content must participate in existing bounded page accounting rather than bypass it.

#### Bounded repair design using current supported OMP APIs

Independent Opus review rejected the earlier upstream-export prerequisite as unnecessary scope. The required user outcome is meaningful intent, progress, async state, readable rich content and long details—not arbitrary custom-renderer/Tern visual parity. Preserve ST-4's no-required-OMP-change rule. `getAsyncJobSnapshot()` already exposes job id/type/status/label/intent/command/caption/start/end (`extensions/types.ts:754`, `session/agent-session-types.ts:80–112`); persisted tool calls retain intent (`packages/ai/src/types.ts:1063`). These complement the tool lifecycle events and content parts described above. No external NativeToolView export is needed for this repair.

The extension must publish typed tool start with intent, coalesced partialResult updates, final result content/details and isError, streaming assistant text, supported image/text parts, async job snapshots and async result messages. The normal card uses intent or tool name, clear pending/running/done/error/cancelled state and readable content. Args and intentional JSON remain available under disclosure, not a raw protocol envelope as normal UI. Do not duplicate arbitrary tool-specific native hooks or claim their full visual parity.

For reconnect and branch/reset, capture supported `sessionManager.getBranch()`, async snapshots and the extension's current running-tool map synchronously with follower enrollment and cursor assignment. Subsequent deltas retain stable session/generation/message/call/job ownership. A gap or stale generation marks observation incomplete and requests a current snapshot, never merges old branch results. Preserve native history separately. Bound snapshot, frames, tree depth/nodes, text/blob sizes, in-flight queues and retained state; coalesce intermediate progress but preserve latest and terminal states. Long details page in order at Unicode boundaries without silently clipping.

**Vox components:** carry this structured current-API projection through the extension/mirror, sealed Session activity validation and split/join, index/fold/query, pagination, UniFFI and native Swift views. Preserve author/occurrence ownership, update identity, branch replacement and existing access checks. The TUI consumes a readable form of the same projection, not a separate tool renderer. Preserve non-OMP paths and existing approvals/questions. No private renderer imports, second runtime or executable tool behavior is introduced by viewing.

**Media:** a semantic blob reference is not a transferable path. `TERN_BLOB_DIR` is local to the machine running Tern and SSH does not forward it ([transport §Through Tern’s blob cache](https://docs.stencil.so/tern/protocol/transport.md#through-terns-blob-cache)). Use Vox’s existing authorized Session/file transfer path where it meets the contract, with an explicitly Session-scoped, access-checked blob reference and bounded on-demand byte transfer; verify declared size, MIME as appropriate and SHA-256 before display, limit concurrency/storage, and expose unavailable/too-large/unsupported media honestly. Check permission again on fetch and discard stale in-flight results after Session/branch/access changes. Never dereference a remote `file://` path as a local path or fetch arbitrary URLs automatically. Tern’s documented 16 MiB blob bound is a reference, not permission to bypass Vox’s own tighter limits. No code or terminal control sequences from untrusted data are executed.

#### Acceptance and inverse safety conditions

Run the existing actual-product OMP + Vox native UI journey on isolated scratch HOME/DATA/CONFIG roots against the reviewed candidate and current supported OMP APIs, not a mock, invented exporter or internal-count-only proof:

1. In a real Session, show user and assistant content as readable prose and a real tool with distinct native intent/target; start, visible partial progress and final output update the same identifiable item without JSON envelopes. 4. From a live active branch, switch/tree/reset while updates are in flight; reload/reconnect and see only the current post-reset branch plus correctly linked current work. ## 10. Room member removal request

### Requested room-admin member removal — 2026-11-06

The operator requested a way for the admin to remove a node member from a room, after deleted/reinstalled identities remained in the room and generated stale reach/trust warnings. This is a product requirement change, not an existing supported command.

#### Existing boundary

ADR-007 G-21 expressly forbids admin removal of a member; G-5's `vox room admin remove` only revokes an admin role. ADR-012 N-27 leaves ciphertext-level presence intact when individual trust is removed. ADR-035 CT-12/14 separately requires replacement fingerprints to remain distinct and stale rosters not to restore removed membership or drive privileges. No real trust, membership or computer policy has been changed by this investigation.

#### Requested outcome and proposed safe semantics

- A room's creator or authorized admin is to be able to remove a particular member identity using its exact fingerprint, with UI that distinguishes a retired identity from a similarly named replacement.
- This is to be a signed room-governance action, not a local UI hide or a forged departure signed as the removed node. Ordinary members must not be able to remove other members; removal must not silently expand delegated admin powers beyond the amended contract.
- Enforcement is to stop new room access, Session read/drive and inclusion in active member/claim-agreement/reach work once the removal is locally known. It must not erase existing signed messages, signatures, fork evidence or claim history, nor claim to erase anything already read by the removed node.
- Room removal must not edit global node/computer trust or affect unrelated rooms. A reachable online peer and an offline peer must expose honest pending/applied removal status rather than claiming instantaneous global convergence.
- The old room passphrase alone is not to undo removal. Re-admission of that exact removed identity needs a deliberate authorized room decision; a replacement fingerprint remains a different identity, not inherited authority. The creator's root role and removal/re-admission precedence require explicit definition in the source amendment before implementation.
- Obsolete member reach warnings should disappear because room membership changed, not because failures were suppressed. Existing unrelated key-delivery/governance failures remain defects to repair separately.

#### Required engineering proof

After the ADR-007/012 governance amendment and independent task/design review, exercise actual shipped binaries and the native member UI: admin removes an old member; remaining peers exchange distinct new posts; old member cannot read/drive/rejoin merely using the old passphrase; non-admin removal is refused; historical messages remain visible; offline-peer application is honest; unrelated rooms continue working. Extend existing applicable room/governance journeys rather than add an internal-value gate.

Task #1171 now tracks this request. The independently reviewed ADR-007/012/031 amendments
and subsequent private-floor/fork clarifications define the accepted design; implementation
and end-to-end qualification remain incomplete. No candidate acceptance or release is claimed.
This request is additional to, not a substitute for, the active delivery incident and
leave/rejoin integrity repair.
