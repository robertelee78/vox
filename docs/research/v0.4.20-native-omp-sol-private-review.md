The public Session-floor Entry offers a smaller binding than duplicating both restoration hashes in every key grant: bind the private key signature to that exact Entry hash, then validate its ancestry against both current restoration identities. This needs provenance retained by the floor index.

Two concrete gaps remain: Drive rotation checks global trust holders rather than room membership, and the OMP guard can become true again after remove/readmit because it checks current sets without a captured authorization generation.
## Finding

**Existing authentication does not bind private key delivery or native Drive capability to both current restoration identities.** Author restoration alone is insufficient.

A minimal extension can reuse the **existing public Session-floor Entry** as the recipient-specific authorization statement: sign its exact Entry hash into the private SKDM. The floor’s validated public ancestry can then bind both author restoration and recipient readmission. No private activity needs to enter the public DAG.

## Verified source facts and missing bindings

### 1. Private Record authenticates authorship, not restoration

`crates/vox-core/src/node/sessionstream.rs:22-147` defines:

```text
signing input:
  ASCII("vox/private-session/v1") ||
  CBOR([room, GroupMessage_wire])

wire:
  [1, room, GroupMessage_wire, root_signature]
```

`Record::verify` checks room, author fingerprint, drive namespace and signature. It does **not** check restoration identity or expected current epoch.

The GroupMessage authenticates:

```text
[drive_channel(room), epoch, author, chain_id, iteration]
```

through its AEAD/signature, but contains no public ancestry or restoration hash  
(`crates/vox-core/src/group/message.rs:44-120`).

Consequences:

- Neither `chain_id` nor `iteration` proves that input followed readmission.
- `attention_after` cannot supply the missing proof: it is explicitly local-only  
  (`crates/vox-core/src/node/channel/private_session.rs:142-150`).
- Variant 2 is different: it preserves an actual signed public Entry  
  (`sessionstream.rs:69-80,135-147`). Its real ancestry remains independently checkable.

### 2. SKDM names no recipient or restoration

`crates/vox-core/src/group/skdm.rs:87-116,225-250,322-359` signs:

```text
ASCII("vox/skdm/v1") ||
CBOR([
  channel, epoch, author, chain_id, iteration,
  chain_key, signing_pubkey, [sign_algo, aead_algo]
])
```

There is **no recipient**, author-restoration hash or recipient-readmission hash.

The pairwise session protects delivery to its cryptographic endpoint and binds channel/epoch; it does not establish that endpoint’s current room-restoration identity  
(`crates/vox-core/src/pairwise/session.rs:5-11,65-81`).

The store-and-forward KeyPackage adds:

```text

```

but opening it returns an unverified SKDM; the recipient field adds no restoration binding  
(`crates/vox-core/src/node/keypackage.rs:64-119,170-207`).

### 3. Public Session floors provide a reusable authenticated bridge

The exact floor body is:

```text
GROUP_MSG_SIGN_DOMAIN ||
CBOR([
  "vox/session-floor/v1",
  room, author, recipient, epoch,
  generation, iteration, first_seq, membership
])
```

Its enclosing root-signed public Entry authenticates the body  
(`crates/vox-core/src/node/channel/session_floor.rs:1-58`).

Public Entries also sign `prev_hash`, backlinks and `seen` references  
(`crates/vox-core/src/log/entry.rs:175-250,323-329`). Control publication uses that Entry machinery  
(`crates/vox-core/src/node/channel/pending_text.rs:743-764,896-929`).

**Missing consumer binding:** the floor catalog retains only:

```text
(author, recipient, epoch, generation) → (membership, iteration, first_seq)
```

not the authorizing Entry hash/restoration provenance  
(`crates/vox-core/src/node/drive.rs:83-87`;
`crates/vox-core/src/node/channel/session_projection/floor_index.rs:44-59,178-200`).

Moreover, `membership` comes from the member’s self-authored `Presence.back` sequence, not creator readmission  
(`crates/vox-core/src/node/channel.rs:8594-8622`).

Thus the **existing signed context is sufficient in principle**, but the existing floor API/index does not expose or enforce it.

### 4. Existing receive/replay gates cannot distinguish restored input

`PendingUpgrade::permitted_to` checks recipient membership, floor boundaries and generation continuity—not current author/recipient restoration  
(`crates/vox-core/src/node/channel/private_session/pending_upgrade.rs:1034-1099`).

The same missing binding reaches:

- authorization/preview: `pending_upgrade.rs:532-557`;

- unread replay through `receive`: `pending_upgrade.rs:1358-1381`;

Receiver installation authenticates the SKDM’s author/channel/epoch, then stores a receiver keyed by author/generation. The drive-existing-receiver branch returns unchanged without a restoration-specific authorization decision  
(`crates/vox-core/src/node/channel/pending_package.rs:405-449,747-803,860-888`).

### 5. Membership exclusion alone will not rotate Drive keys

`PendingSession` captures room members separately from the global Drive holders. Rotation calls:

```rust
self.drive.lost(&self.holders)
```

not the intersection with current room membership  
(`crates/vox-core/src/node/channel/pending_session.rs:261-283,323-328,535-543`).

`DriveState::lost` examines only `delivered` recipients  
(`crates/vox-core/src/node/drive.rs:247-258`).

**Concrete cutover defect:** filtering a removed member out of `drive_members()` while retaining global trust does not itself force rotation. A delivery-ledger-only trigger also cannot establish that no key escaped through an already-published package.

Rotation must follow the validated authorization cut, independently of delivery bookkeeping. Real entropy already has a producer: `SenderChain::new` generates a random chain key and signing key  
(`crates/vox-core/src/group/state.rs:76-105`). A larger counter is not a substitute.

### 6. Native OMP capability checks have an authorization ABA gap

`OmpDriveGuard` checks:

- daemon attachment generation;
- identity/unlocked state;
- current global Drive membership;
- saved room instance and current peer membership;
- exact Session registration/route.

It captures **no room authorization generation or restoration pair**  
(`crates/vox-tui/src/host.rs:2616-2668`).

Deferred text is retained behind a random capability ID. Materialization removes the ID once and rechecks the guard  
(`crates/vox-tui/src/omp_mirror.rs:75-96,391-431,458-482`).

**[INFERENCE: adversarial schedule]** Within the same attachment, room instance and registration, remove/readmit can make the current-set predicate false and then true. An unconsumed old capability can therefore become allowed again. Random IDs provide unguessability/one-use consumption, not authorization-generation binding.

The extension’s fence contains Session/route generation and branch/reset ancestry—not room authorization  
(`crates/vox-tui/assets/omp-extension.ts:70-81`). It materializes Drive text at `:581-595`; provider/acceptance handling at `:604-628` has no corresponding room-generation check.

Existing private native guards do not fill this gap: `CurrentPrivateGuard` checks the keyring nonce and deadline only  
(`crates/vox-core/src/node/actor/history_demand.rs:2271-2314`).

## Minimal exact wire/API proposal

### A. Define the validated restoration identity

For identity \(x\), let \(R_x\) be its **current covering creator-readmission Entry hash**, or absent only when no validated removal requires restoration.

Authorization requires current ordinary membership/trust **and** valid covering evidence. A hash supplied by an input is never itself authority.

### B. Retain the proposed Record v3

```text
signed:
  ASCII("vox/private-session/v3") ||
  CBOR([room, GroupMessage_wire, R_author_or_null])

wire:
  [3, room, GroupMessage_wire, R_author_or_null, root_signature]
```

`null` means exactly CBOR `0xf6`, not a zero hash. The current CBOR subset needs explicit null support (`crates/vox-core/src/cbor.rs:103-108`).

Before any **new** decrypt/install/forward:

1. Check author, room, drive namespace and current epoch.
2. Verify the root signature.
3. Require the signed restoration identity to equal the current validated author restoration.
4. Independently authorize the recipient through its current grant.

No ancestry is invented for v1.

### C. Add one signed hash to private SKDMs

Use the existing Session-floor public Entry \(F\). Require:

- exact room, epoch, sender and recipient;
- matching generation and release iteration;
- validated signed ancestry descending from both applicable restorations;
- current authorization of both identities.

Proposed private SKDM:

```text
B = [
  drive_channel(room), epoch, author, chain_id, iteration,
  chain_key, signing_pubkey, [sign_algo, aead_algo],
  floor_entry_hash
]

signature input:
  ASCII("vox/private-session-key/v1") || CBOR(B)

wire:
  existing SKDM struct frame, version 1,
  CBOR([B's nine fields, composite_signature])
```

This adds **one digest**, rather than duplicating recipient and both restoration hashes. The referenced floor already signs the recipient; its ancestry supplies the restoration bindings.

Required API:

```text
validate_private_grant(floor_entry_hash, expected_authority)
    -> ValidatedPrivateGrant

release_for(signer, recipient, ValidatedPrivateGrant)
    -> private SKDM

install_private_key(private SKDM, ValidatedPrivateGrant, captured_generation)
```

The floor index must retain the source Entry hash and restoration-scoped provenance. Continuity must not join grants across different restoration identities.

Ordinary room SKDMs remain a separate use. New private-namespace input must not fall back to the old unbound SKDM format.

### D. Bind pending work and native capabilities immutably

Capture, before queuing raw input:

```text
(room, epoch, author/driver, recipient/session-owner,
 author_restoration, recipient_restoration,
 validated_room_authorization_generation)
```

Retain existing keyring-nonce, attachment, room-instance and Session-route checks.

Revalidate the **captured** identity at key installation, decrypt, Store commit, record/key egress and native Drive handoff. Never replace it with a newly sampled identity while retaining old raw bytes.

For OMP, carry the same captured identity through:

```text
Drive ingress → Cmd → Deferred → materialize → native delivery/commit
```

Both endpoints matter: driver restoration is not Session-owner restoration. A fresh key/grant/capability must not upgrade an old queued request.

The final native check must fence the actual irreversible delivery boundary—not merely add a rejection after text has already reached the provider.

## Can one readmission hash cover all removals?

**Yes, under a proved single validated creator chain; not from sequence-number comparison alone.**

The proposed public contract permits concurrent delegated removals but makes readmission creator-only  
(`docs/adr/ADR-007-membership-consent-and-admin-governance.md:225-243,255-264`).

For each currently valid removal \(m\), suppose a valid creator readmission \(r_m\) supersedes it. Choose the latest such readmission \(R\) on the validated creator chain. Then:

\[
m \prec r_m \preceq R \quad\Rightarrow\quad m \prec R.
\]

Thus one hash can represent **cumulative coverage**, including earlier readmissions inherited through creator-chain ancestry. A concurrent/later uncovered removal still denies access.

Existing feed validation checks real hash links; signed skip certificates can prove ancestry  
(`crates/vox-core/src/log/feed.rs:225-263,427-468`). Verified equivocation freezes an author rather than establishing a competing order  
(`crates/vox-core/src/log/dag.rs:55-59,668-703`).

Required conditions:

- coverage derives from validated supersession facts plus authenticated creator-chain ancestry;
- comparing `seq`, timestamps or hash order is insufficient;
- a missing/forked/unvalidated reference cannot establish coverage;
- malformed/missing evidence leaves that input inert and triggers bounded recovery—not a room-wide barrier.

## Historical rows versus new input

`receive` already returns for an existing rendered row before trying another decrypt  
(`pending_upgrade.rs:1258-1264`). Restore rebuilds indexes from stored wire/rows  
(`:674-710`).

Preserve that distinction:

- Already accepted `Stored.row = Some(...)`: historical data; retain it under ordinary reader permissions.
- `row = None`, pending replay, newly received wire or deferred raw Drive: not accepted history; require current bindings.
- Cached content must not mint a current key grant or Drive capability.
- Page authentication currently precedes its cached check (`page.rs:153-175`). Adding a universal v3 gate there would incorrectly classify cached v1 rows as new input.
- Legacy variant 2 may use its genuine public ancestry; it receives no invented private ancestry.

## Consumer-visible adversarial inverses

These are required scenarios, **not exercised results**:

| Adversarial input | Required inverse |
|---|---|
| Author removed; old Record/key arrives afterward | No new render, decrypt, key install or forwarding. Previously accepted local rows remain readable under ordinary permissions. |
| Author readmitted; replay old v1/raw key | Still inert. A distinct currently bound publication succeeds. |
| Recipient readmitted; remaining author’s old grant replayed | Reject old grant; accept only the current recipient-bound grant. Do not reuse the old floor merely because its membership scalar matches. |
| Queued OMP ID spans remove/readmit | Old ID/raw text never materializes or commits. A separately authorized new request succeeds. |
| New valid concurrent removal arrives after a cited readmission | New input loses authorization; no timestamp or arrival-order exception. |
| Forged/wrong-room/missing ancestry | That input remains inert; unrelated members/rooms keep working. |
| Cached accepted Record is encountered again | Historical lookup only; no new capability, ratchet reset or destructive migration. |

## Remaining uncertainty

- Root-removal/readmission enforcement is proposed, not implemented in the inspected paths. The single-hash argument is a design proof obligation, not observed product behavior.
- The one-hash SKDM proposal depends on retaining and validating the floor’s necessary causal evidence. The current tuple-only floor API is insufficient.
- The extension shows the native provider/acceptance callbacks, but this source slice does not establish an OMP API that atomically fences provider dispatch against room-authority changes. A post-dispatch check cannot undo disclosure.
- Fresh entropy is an honest-producer obligation; neither a restoration hash nor generation counter proves randomness.
- Unaware partitions and previously disclosed plaintext/keys remain outside any instantaneous revocation promise.
