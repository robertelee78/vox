## The prior blocker is resolved

A creator cutoff no longer disables a re-added or readmitted admin forever (G-29 lines 226–233). An act by a delegated admin is valid only if, for every creator removal or revocation that applies to it, it either:
- lies in that cutoff's strict causal past, or
- descends from the matching root-only restoration, which itself descends from that cutoff: creator readmission after a removal, or a fresh creator delegation after a revocation.

The ordinary membership, scope and delegation checks still apply to restored authority.

I walked through these cases against the text:

| Case | Result |
|---|---|
| Revoke, then re-add | New acts that descend from the fresh delegation are valid. |
| Revoke, re-add, revoke again | An act made after the re-add but concurrent with the second revocation is invalid. The second cutoff has no restoration after it. |
| Remove, then readmit | New acts that descend from the readmission are valid. G-28 keeps the delegation in force, and G-30 already requires readmission to descend from every removal it supersedes. |
| Remove, then re-delegate only | Stays inert, because the restoration has to be the matching kind. |
| Forged act citing only pre-cutoff parents | Invalid both before and after restoration. It cannot descend from a restoration that comes after the cutoff. |

**No cycles or ordering problems.** Cutoffs and restorations are root-only, and the creator cannot be removed. The creator's own facts sit on its single author chain, so they are totally ordered. Validity depends only on the validated causal set, so replay and delivery order converge, and facts with missing ancestry stay inert under the existing rule.

**Remaining limit, stated honestly:** two delegated admins removing each other at the same time both stand. The creator fixes that with a removal or revocation.

**The other documents now agree.** G-31 (lines 287–295) and LS-21b (lines 189–193) describe the same restoration rule. G-32 (lines 316–320) now tests revoke then re-add and remove then readmit, and checks that old-parent forgeries have no effect after restoration.

## OpusFinalOmpDesign

**Scope verdict: P420-OR / FX-58 at `0f5988648` is APPROVED as a design.** This does not approve implementation, consumer acceptance or publication. I checked the delta against `51a276908` and source at `ec00fa91b`, with no edits, builds, tests, formatters or tracker writes.

**The last blocker is resolved.** It was that after a second mismatch, nothing was left to notice a matching daemon. ADR-029 lines 401-410, the design doc's line 23 and the last acceptance bullet now agree:
- **The successor stays alive.** A successor that also mismatches remains the lifetime owner. It reports a fixed unavailable/mismatch category with update guidance and keeps the capped short hello probes. It never reports Ready or allows writes until a full strict handshake succeeds.
- **Its inputs exist in source.** `greet` already returns the daemon's pid and version before the strict check (`daemonipc.rs:2142-2152`, checked at 2080-2092). So the successor can tell a new daemon apart without bypassing the handshake.
- **No writes leak while mismatched.** Register and prompt children run the same current binary, so they hit the same version check. The cold-staging path returns on a version error and does not start a daemon (`daemon_client.rs:117-119`).
- **Recovery needs no restart.** The first successful handshake ends the episode, so a matching daemon recovers without an OMP prompt or restart. Each later update gets its own single successor.
- **No conflict with the fail-closed rule.** Ordinary spawn or pipe failure still fails closed. A helper that is alive but mismatched is not a failed helper, so this does not contradict OR-5's "If the helper fails, Vox is unavailable" (line 410).

**Status of the original four blockers:**
- **ORA** (no attach, daemon can exit): resolved by the read-only hello probe.
- **ORB** (typed retryable refusal, exit 75/1, protocol 10 → 11, v0.4.19 upgrade proof): resolved.
- **ORC** (live owner for every write, reload refusal, confined directories): resolved.
- **ORD** (one watcher per instance, mutation-lock handoff, drain and cleanup): resolved.

**Non-blocking (P3):** a register child refused for a version mismatch during the episode is classed as a permanent protocol refusal. Line 406 already requires recovery without a prompt, so it would be clearer to say that refusal clears when the episode ends. Then the watcher's first matching Ready runs one register for the unconfirmed generation.

**Overall correctness:** correct, at confidence 0.8. FX-58's design blockers are closed. Implementation and the consumer acceptance in the design doc are still required before release.
