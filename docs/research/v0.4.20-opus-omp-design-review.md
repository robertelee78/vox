**NOT APPROVED.** I reviewed ADR-029 P420-RB/OR/OD/OP, RCA §§3 and 6–8, and ADR-038 FX-55 and FX-58–60, at proposed commit `ad27e39a0`. This approves no implementation.

I checked the claims against Vox source at `ec00fa91b` (`/opt/vox` is clean), OMP source at `dc295ad286` (package version 18.16.0), and `/Applications/Tern.app` 0.9.12. I did no edits, builds, tests or real-profile runs. Lines marked [INFERENCE] are my reading, not observed behaviour.

**Scope answers**
- **Registration:** it can be fixed with small changes, with no new receipt format and no subscription framework. The record correctly keeps the actual same-ID red→green (resumed session, node absent → Ready) separate from Vince's fresh-daemon-timeout and pre-envelope-poison path. The source supports the poison mechanism, but it is not proven to be the historical trigger. P420-OR-3 and OR-4 are sound as written.
- **Repository:** canonical `room none`, atomic compare-and-swap (CAS) scope replacement and native rebind are justified. Today `room_map::bind` removes the old block and then appends a new one: two writes, no lock, and a moment with no block (`room_map.rs:417-460`). RB-4 fixes that. RB-3's authorization prerequisite is extra scope.
- **Drive:** treating explicit Drive under the existing capability as operator input matches ADR-029 DR-1.2. Ordinary room attention stays foreign data. OD-4's controls, and its rule against claiming an answer that isn't evidenced, are correct. OD-2's conditional upstream prerequisite can be settled from source now.
- **Presentation:** the record wrongly makes the user's outcome wait on an upstream OMP export. A good semantic presentation can be built on OMP APIs that exist today. Full per-tool parity with Tern is the only part that needs more.

**Findings**

1. **Do not gate OMP presentation on a new upstream OMP export** (P1, confidence 0.85; ADR-029 lines 417–432 and the matrix row at 462; ADR-038 lines 1446–1450).
   - **Problem:** OP-2 and OP-3 require an OMP-owned export, and the only acceptance row runs "With a supported semantic exporter". That exporter does not exist, so the user's outcome — no raw JSON, meaningful intent, progress, async state and rich content — could never be accepted. The record also weakens ST-4, which still says integration "MUST NOT require changes to Oh My Pi itself" (line 255).
   - **What exists today:**
     - Tool start events carry a separate `intent`. Update events carry `partialResult`. End events carry `result` and `isError` (OMP `types.ts:1242-1266`; forwarded in `lifecycle-mirror.ts:154-184`).
     - The result is an `AgentToolResult` holding text and image content parts plus `details` (agent `types.ts:1047-1060`).
     - `message_update` streams assistant text.
     - `ctx.getAsyncJobSnapshot()` returns each job's id, type, status, label, intent, command, caption and start/end times (OMP `types.ts:754`; `agent-session-types.ts:80-112`). The RCA does not mention it.
     - `ctx.sessionManager.getBranch()` is the read-only branch Vox already uses. Persisted tool calls keep `intent` (ai `types.ts:1063`). A follower can therefore resnapshot inside the same synchronous handler. [INFERENCE] JS runs one event loop, so there is no snapshot/event race.
   - **Where the loss happens:** Vox's extension stringifies `args` and `result`, drops `intent` and ignores updates (`omp-extension.ts:636-645`).
   - **Minimal change:**
     - Make the current-API projection the required P420 outcome: intent-or-tool-name heading, live and coalesced partial progress, a pending/running/done/error/cancelled status, text parts as Markdown/code, image parts, and async jobs from the snapshot plus async result messages. Show JSON args only in a disclosure.
     - Make branch/reconnect resnapshot come from `getBranch()` plus the extension's own map of running tools.
     - Keep ST-4 unchanged and drop the qualification at lines 287–288 and 422.
     - Turn OP-2 and OP-3 into a non-gating note: per-tool `describeCall`-style heads for arbitrary or extension tools would need a future OMP-supported API and must not be claimed now.
     - Rewrite the acceptance row against the current-API projection.

2. **Resolve RB-3's open authorization prerequisite with the existing OS-account boundary** (P1, confidence 0.8; ADR-029 lines 311–320).
   - **Problem:** RB-3 asks for a still-unspecified "enforceable local operator authorization boundary" that defeats same-user socket access, and the closing paragraph lists it as unresolved. That leaves FX-55 with no executable design.
   - **Conflict with accepted ADRs:** ADR-026 C-1 makes the control socket mode 0600 with a uid check. C-6 and line 388 say "the OS account is the boundary (ADR-001)". Passphrases for attach and keyring changes, and today's `RoomBind`/`RoomDecline` map writes (`host.rs:5082-5087`), already rely on that boundary.
   - **Minimal change:** replace the last two sentences with a decision. Replacement is a distinct daemon verb used by Vox.app and the operator CLI. CLI entry points refuse agent-marked callers, as already specified. Same-uid access is the accepted boundary; no person attestation and no new authorization mechanism. Make RB-2's refuse-and-explain on ambiguous scope the decided behaviour so the "ambiguous-scope UI" is no longer an open prerequisite.

3. **Use the existing `--attention-register` exit status as the registration receipt** (P2, confidence 0.85; ADR-029 lines 341–349).
   - **Problem:** OR-1 requires a new structured receipt naming node, session, route/generation and admission, and the RCA allows hook/daemon IPC changes. Source shows that is unnecessary:
     - Register-only returns `Ok` only after a non-Attaching `SessionRegistered`. Cold-start `Starting`, `Attaching`, `NotAttached`, `NoNode`, a timeout and refusals all return `Err` (`agent_hook.rs:2438-2493`, `2050-2056`).
     - The CLI maps that mode's `Err` to failure (`cli.rs:3358-3365`).
     - The extension's `hook()` resolves only on exit 0 with the same `generation` and `current()` at close (`omp-extension.ts:255-274`). The route token changes only in `retire()`, which also increments the generation (`:289-300`).
   - **Actual defects:** `register()` discards the outcome (`.catch(() => {})`, `:279-287`), stderr is ignored, and no per-generation state is kept.
   - **Minimal change:** define the receipt as "register-only exit 0 for the child spawned under this generation, still `current()` at close". Track unregistered/pending/registered/failed per generation and surface bounded stderr. No new IPC or receipt format.

4. **Make prompt/use the recovery trigger; drop the open Subscribe option and restart invalidation** (P2, confidence 0.75; ADR-029 lines 350–359).
   - **Problem:** OR-2 says "if needed, use the existing daemon Subscribe channel" and "invalidate receipts after daemon restart/reattach", but never decides. Source facts:
     - No CLI command streams `DaemonEvent` to an external process. Only the in-process TUI `DaemonCore` subscribes (`live.rs:557`), so an extension would need a new long-lived helper mode.
     - Subscribe carries only Attached/Detached (`daemonipc.rs:466-480`) and cannot help while the daemon is absent, as in Vince's timeout.
     - The posting guard checks the on-disk registration (`coord.rs:160-165`). I found no source path that removes it on daemon restart [INFERENCE], and the adapter cannot see a restart without that helper.
     - Today a prompt only awaits a registration already in flight and never starts one (`omp-extension.ts:463-482`).
   - **Minimal change:** on activation and before each real prompt's prepare, if the current generation is not registered, call the existing `register()` once, coalesced, then recheck the fence. A pre-envelope "no longer registered" failure resets the state to unregistered. Delete the restart-invalidation clause.
   - **Open choice:** if idle urgent-wake reachability before the next prompt is required (ST-4), state it explicitly and name the new CLI helper. Otherwise drop the Subscribe option and "daemon reattach" recovery from the matrix.

5. **Specify Drive delivery on the existing guarded context path; drop the conditional upstream prerequisite** (P2, confidence 0.75; ADR-029 lines 374–388).
   - **Problem:** OD-1 asks for "OMP user-prompt semantics" and OD-2 makes a new native API a prerequisite if void `sendUserMessage` cannot carry the guard. The existing path already ties the guard to consumption:
     - an aside wake (`omp-extension.ts:83-85`);
     - capability materialization at the `context` event (`:563-570`);
     - exactly one marker counted in the provider request (`:598-607`);
     - acceptance at the assistant's `message_end` (`:613-627`).
   - **Supported fix:** `ContextEventResult.messages` takes any `AgentMessage` (`types.ts:1686-1688`), so the extension can inject explicit Drive text as `role: "user"` with a node-provenance wrapper instead of "not the user". By contrast, `sendUserMessage` takes text immediately and would bypass deferred materialization. The unacknowledged upstream dependency also conflicts with ST-4 again.
   - **Minimal change:** keep the wake → context-time materialization → marker-acceptance path. Change only the role/wrapper for explicit Drive text. Document the aside timing: an idle session starts a turn; a streaming session gets it at the next step boundary. Delete the upstream prerequisite sentence.

6. **Define which native evidence links a Drive operation to its response** (P2, confidence 0.65; ADR-029 lines 389–398).
   - **Problem:** OD-3 requires "an identified native turn/step" and "an answer only with a defensible native causal association" but never says what qualifies. Implementers will either never show anything beyond accepted or invent a link.
   - **What source supports:** the accepted criterion already pins one assistant `message_end` produced by the single provider request that carried the operation's marker (`omp-extension.ts:598-627`).
   - **Minimal change:**
     - Define the step association as that `message_end`, published as a typed, ID-bearing event over the existing authenticated mirror follower and written as `drive-result.of`.
     - Show that message as the response step. Never label a later or unmarked reply "answered".
     - Remove the separate "answer" state unless a further native criterion is named.

**Verdict:** incorrect. Registration and repository fixes can stay small, and the Drive operator-input model is right. But presentation is wrongly gated on an upstream export that contradicts ST-4. The registration, authorization and Drive-delivery designs also leave open or extra prerequisites where existing source already gives a concrete design. Confidence: 0.8.

**Checks for after implementation:** an actual-native OMP resumed absent-node → Ready red→green, and the fresh startup-timeout plus pre-envelope prepare case. Then actual Vox.app/TUI Sessions showing intent, partial progress, async jobs and text/image parts without raw JSON. Then idle and streaming private Drive showing queued → accepted → linked step. Last, Not This Repo / rebind CAS conflicts from Vox.app and the operator CLI.
