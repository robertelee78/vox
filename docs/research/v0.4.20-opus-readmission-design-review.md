**Verdict: APPROVED for the design. NOT APPROVED for the ADR wording as it now stands in the working tree.**

Making readmission strictly forward and sender-local is sound. It breaks no security requirement, it fits G-27, G-31 and SA-14's no-backfill rule, and the code matches it. The proposed text has five problems, listed under blockers below. All five are wording fixes, and none needs a design change.

This was a read-only review: no edits, builds, tests or vox runs. Line numbers refer to the working tree at 409124146 plus a4e03b263 and may drift.

## Answers to the questions

**Are pre-readmission chains released some other way?** None of the paths I checked release such a chain after the sender has applied the readmission. The paths I checked:
- **Rotation.** In `prepare_room_removal_rotation` (`pending_text/consent.rs`), any readmitted target that held an entitlement at the cut is reset to `(next_chain, 0)`, and its rows in SEG_HISTORY and SEG_DELIVERED are cleared. This also happens when the removal and the readmission arrive in the same fold: `member_fold.rs` records the sender cut when it accepts the removal (lines 721 and 766), and the generation advances when anything changed (line 1013).
- **History delivery.** `history_skdms` never releases a chain below the target's entitlement, so even a stale SEG_HISTORY floor cannot pull an old chain.
- **Queued consent.** A consent prepared before the readmission fails when it commits, because its removal fence no longer matches. `prepare_pending_consent` also refuses while a rotation is still needed.
- **Key packages sealed for the target.** These are refused while the target is removed, and a stale removal generation fails the check at commit.
- **Held SKDMs.** For any once-removed target, `prepare_owned_consent_key` (`consent_release.rs:569-581`) goes straight to forward-only `skdm_for_consent` and never reads `consent_keys`.
- **Third parties.** Only a chain's author can release its keys.

**Senders that haven't applied the readmission.** One that applied the removal but not the readmission still sees the target as removed and releases nothing. One that never applied the removal is in the disclosed unaware-partition window and can still release anything, including removal-period chains.

**Cached key packages.** A key package is a log entry (RL-4.1/4.5), so every member replicates it. A package sealed to the target before its sender applied the removal stays on the log. After readmission, aware members sync it to the target through ordinary replication. `package_install` checks only the author's removal and eligibility, so the target installs it. That case is part of the window, but it is not "delivered before", which is what the proposed text says.

**Regressions.**
- Ordinary rejoin without a removal is unchanged: `validated_member_removals` is empty, so the `full`/`now` behaviour is the same.
- A readmitted member with no undelivered debt keeps its journey. If it was entitled at the cut, the rotation gives it the fresh chain from origin. If not, its next ordinary consent gives it the live position (`outbound.rs:189-196`).
- The one intended regression: once an identity has any validated removal in a room, a `--history full` grant to it in that room is downgraded to the live position. This lasts forever for that room, even after a later ordinary leave and rejoin. The grant record stays truthful, because `full_history` is false when there is no plan. But this overrides the accepted ADR-006 S-18 and ADR-023 RL-5.1/5.2 without saying so.

**Silent gap versus ADR-028.** Leaving the gap silent is acceptable in the timeline. It matches the existing render-gating model:
- ADR-007 G-14.3 says a joiner's view "fills in monotonically, per sender" and G-15a that it stays "unreadable to the joiner for good".
- ADR-008 places entries a node cannot read.
- RL-4.4 says messages sealed before a grant stay unreadable.
- ADR-036 already treats a permanently unreadable entry as not to be retried in a loop.

No ADR-028 rule requires a row for each unreadable message, and today the code shows none (`semantic_projection.rs` `prepare_inner` returns `Applied`; `history.rs:518-535`). K-21 only allows warnings backed by evidence, and the receiving node has no evidence that a chain is never coming. A label like "unavailable" there would be the untruthful choice.

What must be surfaced is the readmission claim itself. K-26 says readmission "MUST NOT promise access", so the readmission confirmation and result must say that history is not restored. Release notes must say the same.

## Blockers in the wording

1. **ADR-007:286-292 and ADR-031:345-347** say unreadable messages "MUST be shown as unavailable". That contradicts your refinement and the code. Delete it.
2. **The text silently contradicts accepted rules.** ADR-006 S-18 (lines 97-104) and ADR-023 RL-5.1/5.2 (lines 189-194) say a `full` grant releases every retained generation. G-30 must name these as amended, and S-18 and RL-5.2 each need a one-line cross-reference. Because this changes accepted, built behaviour, operator confirmation really is required.
3. **ADR-031 contradicts itself.**
   - SA-14:329-331 and ADR-007:324-326 still let a floor "strictly prior to that removal" authorise serving history to the recipient.
   - The implementation is stricter: `floor_index.rs:429-433,467` requires, for every removal, a floor that descends from a covering readmission.
   - The new sentence in ADR-031 talks about "sender chains", which is room-key vocabulary, not drive generations.
   - Fix: change the SA-14 and G-31 text to the code's rule.
4. **Two factual errors in G-30's new text.**
   - "Chains delivered before a sender learned of removal" misses key packages that were sealed before but are fetched after readmission.
   - "Sets the restored target's entitlement at that chain" is wrong for a target that held no entitlement at the cut. Its entitlement starts at its next ordinary consent, so the correct phrase is "no earlier than".
5. **G-32:357-358** ("restores only appropriate access") has no acceptance row for this limitation. Add one.

## Exact wording

**ADR-007 G-30** (replace the working-tree block):
> **Provisional v0.4.20 history limitation (lead decision 2026-11-07, pending operator confirmation; amends ADR-006 S-18 and ADR-023 RL-5.1–RL-5.2 for this case).** Readmission restores room sender-key access forward only, per sender. When a sender's validated fold first applies a covering readmission, whether or not it applied the removal earlier, it MUST rotate to a fresh sender chain before releasing another room key. The readmitted identity's entitlement from that sender starts no earlier than that chain. The sender MUST NOT release, re-offer or backfill any chain it minted earlier, whether minted before the removal, during it, or at an unknown time. For an identity with any validated removal in this room, a `full` history grant releases only the live position. Identities never removed keep S-18/RL-5 unchanged. Messages the readmitted node already read stay readable (G-27). Messages it holds no key for are not rendered, as for history sealed before a fresh join (G-15a). Clients and the K-26 readmission action MUST NOT present readmission as restoring history. A sender that has applied the removal but not the readmission releases nothing to the target. Keys a sender released before it applied the removal fall in the disclosed unaware-partition window (G-29, G-31). This covers keys sent directly and keys sealed into a key-package log entry, which ordinary replication can still carry to the target after readmission. A sender that has not yet applied the removal is in that same window. None of these keys can be recalled, and release notes MUST say so.

**ADR-031 SA-14:**
- In the Recipient restoration paragraph, replace lines 329-331 with: "For a recipient with any validated removal, a floor supplies history authority only if it causally descends from a valid creator readmission covering every such removal; a floor strictly prior to a removal no longer authorizes serving or releasing to that recipient (v0.4.20, with ADR-007 G-30)."
- Make the same edit to ADR-007:324-326.
- Replace lines 345-347 with: "Private history the restored recipient already accepted stays readable locally; pre-removal and removal-period private history it lacks is not re-served or rendered."

**ADR-006 S-18 and ADR-023 RL-5.2:** add "except as limited for once-removed identities by ADR-007 G-30 (v0.4.20)."

**ADR-007 G-32:** add:
> A readmitted target with undelivered pre-removal debt reads its already-held messages and new posts only. Exercise this with a sender that applied the removal and readmission separately, and with one that applied both in one offline fold. The target must not read pre-removal or removal-period posts, and a `full` grant must not change this. A never-removed rejoiner, as the control, still receives `full` history. A mutant that re-offers SEG_HISTORY debt or releases the full plan MUST fail the native-view assertion.

## Residual risk
- Removal-period entries whose body is still missing would show "(not received yet)" until the body arrives, and then disappear. [INFERENCE] I believe this already happens for fresh joiners too.
- A `Reoffer` prepared during the rotation window can write a stale SEG_HISTORY floor. Separately, a target with no entitlement at the cut keeps stale SEG_HISTORY and SEG_DELIVERED rows. Neither leaks a key, because `history_skdms` clamps to the entitlement.
- Not reviewed: `pending_recovery.rs`, the sparse `key_debt_after` path, and how the `deliveries` queue survives across a readmission.
