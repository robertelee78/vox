## Remaining blockers for OR (FX-58)

**OR-A. The watcher's subscription stops an auto-started daemon from ever exiting when idle** (P1, confidence 0.85; ADR-029 lines 372–381; design doc steps 1–3).
- **Problem:** OR-5 says the watcher "does not … autostart a daemon". But every accepted socket connection is counted (`ipc.rs:7148`). A Subscribe connection stays counted for its whole life (`ipc.rs:7218-7233`). An auto-started daemon exits only when `slots.is_empty() && connections == 0` (`host.rs:3786-3789`, `daemon.rs:321-326`, idle rule L-8).
- **Trigger:** the first register attempt auto-starts a daemon whose node stays detached or locked. The always-on watcher then keeps that otherwise idle daemon alive for as long as OMP runs. This cost is not stated anywhere, and it contradicts L-8.
- **Fix:** decide it explicitly. Smallest option: hold the subscription only while the selected node is attached. Otherwise rely on the capped 1/2/4/8/16/30-second reconnect and Nodes snapshot. Those connections are short, so the daemon can still exit after its 1 s linger.

**OR-B. A typed "transient" category needs new daemon IPC, and some causes are misnamed as existing** (P1, confidence 0.85; ADR-029 lines 344–351; design doc step 4).
- **Not typed today:**
  - Register-only collapses every error into prose: `AppError::Usage(error.said(..))` (`agent_hook.rs:2056-2059`), then `ExitCode::FAILURE` (`cli.rs:3358-3365`).
  - Timeout, `StillDetaching` and connection-level errors after open are untyped `AppError::Usage` (`agent_hook.rs:2476-2493`).
  - Contention-style refusals arrive as `Refusal::Failed { why: String }`, which also carries permanent failures. Examples: "session registration is busy" (a `try_lock` on the registration lock, `wake.rs:780-783`), "the Session is ending; retry registration" (`host.rs:1645-1650,4206-4211`), and blocked-node refusals.
- **Why it blocks recovery:** OR-5 also makes "inability to … lock" a refusal. So the most likely idle-time failures can only be split from permanent ones by parsing prose, which OR-1 forbids, or by a new typed `Refusal` variant. A new variant is a daemon IPC change, which contradicts "No new receipt format or daemon IPC is required" (line 344–345). If they are treated as permanent instead, idle recovery stops and needs a prompt, defeating FX-58's no-prompt requirement.
- **Fix:** enumerate the exit categories, add one typed retryable refusal over IPC, and amend that sentence.

**OR-C. Every OMP registration now depends on the watcher, with no fallback or upgrade rule** (P2, confidence 0.75; ADR-029 lines 391–404; design doc's ownership section).
- **Problem:** writes are allowed only with a "live lifetime ownership" check, and disk state without it "never grants authority". So with no live watcher, prompt-time and cold-start registration must fail too.
- **Conflict:** the design doc says watcher or spawn failure only means "do not claim no-babysitting availability" (step 5), which implies ordinary registration still works.
- **Upgrade gap:** `vox setup` writes `extensions/vox.ts` (`setup.rs:804-828`), and it can lag the binary; doctor only warns (`doctor.rs:740-751`). [INFERENCE] Already-running OMP processes keep the old extension in memory. The record doesn't say whether a new daemon refuses or accepts OMP registrations that carry no ownership reference.
- **Also unspecified:** where the instance directory lives. The daemon has to open lock files derived from a reference the client supplies. This needs a rule that confines it under the Vox account directory.
- **Fix:** state the reference-less OMP rule (typed permanent "update extension", or explicitly unfenced legacy). State what happens when the watcher can't run, and the confined location of the directory.

**OR-D. One watcher per generation is not the smallest owner** (P2, confidence 0.7; ADR-029 lines 380, 397–400; design doc's resource bound).
- **Problem:** each switch, branch or tree change retires the watcher. It waits for ACK or death, hands over the lifetime lock, then spawns a new process, subscription, snapshot and register before the successor can register. That adds process churn and latency to frequent in-process tree navigation.
- **Cheaper shape with the same fence:** one watcher per extension instance, for the life of the OMP process. It holds the lifetime lock once. Retirement is a serialized "revoke N / install N+1" command under the mutation lock with one ACK.
  - The fence argument still holds: a writer holding the old reference fails the active-reference check under the same mutation lock.
  - Watcher death still ends the instance's authority and rotates the route.
- **Optional simplification:** the existing node `registration_lock` already serializes every `store_checked` writer, on all three paths. It could serve as the mutation lock, so the only new lock would be the lifetime lock.

Everything else in OR-5 is sound:
- The lag-skip claim is confirmed (`ipc.rs:7228`). A 30-second reconciliation snapshot plus capped backoff is a reasonable minimum, and it is not a model poll.
- One coalesced register per generation, no autostart/unlock, stdin-EOF lifetime and same-generation idempotent retry are all correct.
- Retrying a typed transient failure on a fresh Ready snapshot is needed and bounded by the snapshot pace.

## Remaining blockers

**A. FX-54: the rule for legacy identities joining a new room is undecided, and the default is harmful (P1, confidence 0.85).** ADR-023 lines 283–290.
- An upgraded identity has no marker for any room it was never in. A never-member gets nothing from the own-head request (`source.rs:497-503`).
- "Only provenance that establishes a genuinely new author" names only the from-creation fact, which upgraded identities cannot have.
- So every existing identity becomes unknown/read-only in every room it newly joins. It cannot post, grant consent or release its sender key. Today's whole user base could not post in any newly joined room.
- The revision map defers this ("UX tradeoff requires review"); it cannot be scoped away.
- **Minimal fix:** the operator chooses one rule and RL-8.5 states it exactly:
  1. **Strict:** keep read-only, accept the cost and state it in the release notes.
  2. **Evidence-bounded:** record a durable per-identity "tracking since" time at upgrade, while seeding the held rooms. Allow fresh initialization only when the authenticated admitting member holds no feed, own head, kept notice or kept withdraw for this identity, optionally also requiring the signed genesis to postdate tracking plus a skew bound. Disclose the residual fork risk.
  3. **Operator attestation** with the same warning.

**B. FX-53: the admission proposal's wire format is not concrete, and stale RCA acceptance remains (P2, confidence 0.8).**
- RL-8.7 binds the room name into the proposal. Today's proposal has 5 fields under the domain `vox/join-admission-proposal/v1` (`joinstream.rs:110-145`), so this is a wire change. No ADR pins:
  - the new domain and version;
  - the field array and how an absent or invalid name is encoded;
  - that the unsigned `Accepted.name` is no longer used.
- The revision also dropped the earlier "truthful update refusal" for old peers. A new node can detect a version-1 proposal and refuse truthfully before Prepared.
- The RCA's §1 acceptance item 4 still requires ends to stay terminal "after … restart". Item 5 says to "resume" after a "lost receipt after responder commit", which contradicts RL-8.7 case 2 (withdraw, then a newer fresh retry).
- **Minimal fix:** specify proposal v2 in RL-8.7 and ADR-008, require new nodes to refuse version-1 peers truthfully, and correct RCA items 4 and 5.

**C. FX-62: G-31's content filter reintroduces the mutual-removal cycle and leaves the log's structure undefined (P2, confidence 0.75).** ADR-007 lines 261–274.
- Control and governance entries are logged as content entries; for example `pending_control.rs:158` appends one as `EntryKind::Content`.
- For concurrent removals A→B and B→A, G-31 marks each removal ineligible, because its author is the target of the other, concurrent removal. Then neither applies, contradicting G-29's "both stand".
- G-31 also doesn't say whether ineligible entries stay in the log and are forwarded as signed structure. If they are dropped, honest concurrent replies that reference them lose a causal parent at removal-aware peers, and evidence of the removed author forking is lost.
- **Minimal fix:**
  - State that G-29's strict-causal-past authority alone decides whether any governance fact is valid.
  - Apply G-31 eligibility to messages, keys, consents/claims, Presence/Session and service content.
  - Retain and forward ineligible entries as signed log structure (skeleton and ciphertext) without decrypting, displaying or treating them as authority.

**D. FX-62: the mixed-version gate has no mechanism (P2, confidence 0.75).** ADR-007 lines 236–241; ADR-008 lines 183–189.
- "Removal-enabled room" and "negotiated room contract" are not defined anywhere, and no per-room capability negotiation exists.
- Old members keep releasing sender keys to a removed target, so the gate is security-relevant.
- Separately, N-27a requires boards to validate removal, but anchor boards are not members and have no log to check an issuer's causal past.
- **Minimal fix:**
  - Name the authenticated capability signal: a per-member signed advertisement, or an ALPN/bundle capability.
  - Allow offering removal only when every current member's capability is evidenced.
  - After a validated removal, withhold sync and key delivery from members without that evidence, and show which members are blocked.
  - Limit N-27a to member boards, or define evidence that anchors can verify.
