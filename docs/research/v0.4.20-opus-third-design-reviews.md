## Prior blockers

**A (FX-54 rule for legacy identities): resolved.** RL-8.5 now records the operator's ruling verbatim. The rule is:
- First try to recover through the authenticated admitting member.
- If no prior authored history can be derived, start empty automatically, with no prompt and no blanket read-only gate.
- Known signed heads, markers and conflicts still fence writes.
- The residual risk is disclosed.

The `own_history` tags carry this. Kind 0 (no evidence) plus no local history allows empty start. Kind 2 (history known but unavailable), a local marker or contradictory evidence keeps writes fenced. Kind 1 supplies a head that the joiner checks against its own signature and the room/author binding. Existing identities can again post in rooms they newly join.

**B (FX-53 wire format and stale RCA text): resolved.**
- Proposal v2 is fully pinned: the 8 fields, the `vox/join-admission-proposal/v2` + NUL domain, the existing `[12, proposal]` and `[13, hash]` frames, and `Accepted` reduced to `[6, witness]`.
- A head fits easily: the join frame cap is 64 KiB (`MAX_JOIN_FRAME`) and a composite signature is about 3.4 KB.
- A v1 proposal is refused truthfully before Prepared. An obsolete `Accepted` after Prepared is correctly treated as commit-uncertain (case 2).
- Lost `Accepted` (case 2: withdraw, then a newer fresh PAKE retry) is now separate from a verified, persisted `Accepted` (case 3: resume from the retained witness, key wrap and name reservation).
- Explicit cancellation publishes only the node's own Member withdrawal, never a blind log Presence.
- RCA items 4 and 5 now drop the claim that the board tombstone stays terminal after restart, and no longer "resume" without a witness.

**C (G-31 mutual-removal cycle): resolved as specified.** Governance validity now uses only G-29's strict-causal-past rule. Ineligible entries are kept and forwarded as signed skeleton plus ciphertext, without decrypting, displaying or granting authority. This carve-out is what opens the blocker below.

**D (version gate): resolved, and the global gate is sufficient and minimal.**
- `vox/3`, `vox/3-own-recovery` and `vox/3-own-availability` replace all three current ALPNs, with no fallback. The doc's description of the current code is accurate: `provider.rs` offers all three `vox/2*` values on both sides, and `confirm_handshake` maps an unknown ALPN to `SignatureInvalid`.
- New nodes never exchange keys or sync with old ones. That covers D's concern about old members sending keys to a removed target, with no per-room negotiation and no compatibility shim. The remaining exposure is an old partition still talking to itself, and the doc states it.
- N-27a now has only member boards validate removal; nonmember anchors stay discovery-only.
- **No new operator approval is needed.** ADR-026 F-3 (decider, 2026-10-12/10-27) already puts mixed-version wire compatibility out of scope and says old nodes and rooms may be torn down. The previous-release test named in ADR-011 requirement 14 does not exist in the tree.

## Blocking finding (FX-62)

**A removed delegated admin can keep issuing valid governance acts by choosing old causal parents** (P1, confidence 0.7). File: `docs/adr/ADR-007-membership-consent-and-admin-governance.md`, lines 270–281.

- **What changed:** at 37b0ffbf4, G-31's filter covered every entry the target authored, so a removed admin's acts concurrent with its removal were ineligible. The new carve-out exempts all governance facts: "a concurrent or later removal of their author MUST NOT invalidate an otherwise authorized governance act".
- **How it's exploited:** a removed admin B never acknowledges its removal R and authors new acts whose parents predate R. Under G-29 each act is concurrent with R, and B was an authorized member in the act's strict causal past, so the act is valid.
- **What B can do:**
  - remove other non-creator members;
  - rename the room or change its retention or anchors;
  - end the room, which RL-8.2 lets a delegated admin do and which stays terminal.
- **Why the creator cannot stop it:** revoking B's delegation has the same concurrency exemption. A creator readmission loses to any concurrent removal (G-30).
- **How the acts get in:**
  - any member that has not yet seen R;
  - a new joiner that B answers using the passphrase it still knows (nonmember anchors keep advertising B);
  - any colluding member.

  Once in, honest members must keep and forward these acts as valid.
- **Impact:** the removal does not end the governance power of a malicious delegated admin, which is the case FX-62 exists for. G-28's "MUST NOT exercise its delegation while removed" only binds honest nodes.
- **Minimal fix:** add a creator-precedence cutoff to G-29 and G-31. A delegated admin's governance act is valid only if it is in the strict causal past of every valid creator-signed removal of that admin and every creator revocation of its delegation. Acts concurrent with or after those creator acts are invalid and are kept only as opaque evidence.
  - This adds no validity cycle, because the creator is root and cannot be removed.
  - Two delegated admins removing each other at the same time still both stand. State that remaining case as a disclosed limit.
  - The alternative is to keep the current rule and record it as a disclosed limit, but that needs an explicit operator acceptance, which this review does not assume.

## OpusFinalOmpDesign

## Scope verdict: P420-OR / FX-58 is NOT APPROVED as a design

This is a design verdict only. It does not approve any implementation or release. I reviewed `e8ad3b894` against the product source `ec00fa91b`. I made no edits and ran no builds, tests or formatters.

## Were the four prior blockers (ORA–ORD) resolved?

- **ORA: not resolved.** The specific earlier cause is fixed. In source an attached node always reports Ready (`host.rs:4864-4873`), and an attached node keeps the daemon from going idle anyway (`host.rs:3786-3789`). So holding Subscribe only while the node is Attached and Ready adds no idle cost. The backoff gaps also let the 1-second idle linger expire (`daemon.rs:34,321-327`). But the chosen probe, a `Nodes` request, attaches nodes as a side effect, which breaks the same goal again (Finding 1).
- **ORB: resolved.** It adds a typed retryable refusal with a fixed reason enum, used for both initial and deferred writes, with no prose parsing. Exit codes are 0 success, 75 temporary and 1 permanent, other existing categories kept. The protocol goes 10 → 11 with strict version checks, and acceptance requires the actual v0.4.19 upgrade cohort. All of this matches source: `ipc.rs:78`, `cli.rs:3358-3365` and the prose-only refusal `wake.rs:780-781`.
- **ORC: resolved.** Every OMP write, including cold staging, needs a live owner. Helper failure makes Vox unavailable for that extension while OMP stays usable, with no fallback. An old extension loaded without an ownership reference gets a typed permanent reload refusal, plus doctor/status guidance. Ownership files are confined under `.daemon/omp-instances/<opaque id>`, and the wire carries only the opaque ID and generation. An old extension can be identified because it sends `VOX_HARNESS: "omp"` (`omp-extension.ts:51`). Finding 2 is a lifecycle gap next to this one.
- **ORD: resolved.** There is now one watcher per extension instance. Revoke and install commands are acknowledged under a stable private mutation lock. The three `store_checked` paths and deferred writes recheck under that lock and hold it through the write, and a successor drains it before installing a new reference. Mixing the existing nonblocking `registration_lock` (`wake.rs:766-781`) with the new mutation lock cannot deadlock.

## Findings

### Finding 1: the watcher's `Nodes` probe attaches nodes, breaking no-attach and the daemon linger
- **Priority:** P1. **Confidence:** 0.85.
- **Where:** `docs/adr/ADR-029-sessions-and-the-repo-room.md:376-381`; design doc steps 1–3, lines 17-19.
- **Problem:** the design makes `DaemonRequest::Nodes` the probe and the snapshot that confirms Ready. The daemon answers that request with `public_nodes()` (`host.rs:5008`).
  - For every Detached node on disk with no passphrase, not just the selected one, it calls `want(.., Want::Explicit(None), ..)` and waits for the attach (`host.rs:1181-1195`).
  - An explicit attach "stays until detached by hand" (`host.rs:268-269`).
  - Agent sessions are otherwise limited to "only if attached already (ADR-028 K-13)" (`host.rs:272`), and the register hook never sends `Nodes`.
- **Triggers and impact:**
  - The first watcher probe of an auto-started daemon permanently attaches passphrase-free nodes. The daemon then never exits, which defeats ORA.
  - The probe is itself the forbidden automatic attach/unlock, so the "no automatic attach" acceptance fails.
  - An operator's manual detach is undone by the next snapshot, at most 30 seconds later.
  - A "short" probe can block on a full attach and outlive its deadline.
  - If attaching any unrelated node fails, or the attach file can't be read, the whole snapshot is refused. That blocks recovery for a Ready selected node.
- **Fix:** never use `Nodes` or `Status` (`host.rs:5088`) for watching. Use a non-mutating exact-node view instead:
  - Either the hello `attached` list of a fresh short connection opened after Subscribe's `Ok`. That comes from `attached()` (`host.rs:1226-1233`), and Attached ⇒ Ready.
  - Or a new read-only exact-node request in the same v11 protocol bump.
  - Narrow "Never use Hello's attached list" so it covers only the subscription connection's own hello, received before the acknowledgment.
  - Add acceptance: a passphrase-free detached node stays detached, the daemon exits after its linger, and a manual detach is not undone.

### Finding 2: the long-lived watcher breaks after any Vox update, with no successor rule
- **Priority:** P2. **Confidence:** 0.75.
- **Where:** `docs/adr/ADR-029-sessions-and-the-repo-room.md:380-382, 392, 397-399, 415-417`; design doc steps 1, 2 and 5.
- **Problem:** `DaemonClient::open` refuses unless the daemon's version string exactly matches the binary's own (`daemonipc.rs:2080-2092`).
  - The extension resolves `vox` from `VOX_BIN`/`PATH` each time it spawns (`omp-extension.ts:257`). Short-lived register children therefore pick up an updated binary, but the watcher keeps running the pre-update binary for the life of OMP.
  - After any update restarts the daemon, every watcher reconnect fails `IpcHandshake::Version`. The design treats that only as "invalidates the observation" and keeps probing every 30 seconds.
  - Version and protocol mismatch are also classed as permanent, so they stop retry.
- **Impact:** a session whose registration was not confirmed at update time loses idle recovery until OMP restarts or the user prompts, with no explanation. The design also mentions a "successor" watcher but never says when the extension starts one, which conflicts with "helper failure ⇒ Vox unavailable".
- **Fix:**
  - On a handshake version/protocol mismatch, the watcher exits with a distinct category.
  - The extension then starts at most one successor from the current binary at the capped pace, using the existing drain-then-fresh-reference rule.
  - If the successor also mismatches, show the reload guidance and stop.
  - A mismatch should hold back retry only for that daemon instance (pid), not forever.
  - Add acceptance: update while OMP is idle, then the node becomes Ready, and the room ask is delivered without a prompt.

## Non-blocking notes (P3)

- **Successor timing window.** If a successor takes the lifetime lock before installing its own reference, a stale write that still matches the old record would pass the "lifetime held + record matches" check. Existing route checks limit the damage. Requiring the successor to take the lifetime lock and revoke the old reference while holding the mutation lock closes the window.
- **Mutation-lock contention.** Whether busy on the new mutation lock counts as the transient "registration-lock busy" reason should be stated.
- **Cleanup.** No owner is named for removing `omp-instances` directories after their owners have drained.

## Verdict
- **Overall correctness:** incorrect.
- **Explanation:** ORB, ORC and ORD are resolved at design level. ORA is not: the required `Nodes` probe explicitly attaches passphrase-free nodes, which breaks the no-attach rule, the daemon linger and manual detach. Separately, the long-lived watcher has no successor rule and fails permanently across version updates.
- **Confidence:** 0.8.
